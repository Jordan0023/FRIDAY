# RAX54S V1.0.17.144 Unauthenticated RCE/DoS Investigation

## 2026-07-24 proprietary HTTP/SOAP confirmation

The full-system harness was advanced to a stable request/response state using
the vendor-normal no-argument `httpd` launch, the live `smd` message service,
initialized ACOS NVRAM, narrowly modeled NAT/firewall ioctls, and the
persistent certificate paths generated by a production boot. The exact
firmware daemon bound `10.0.2.15:9443` and returned two `HTTP/1.0 200 OK`
controls 20 seconds apart over the host's loopback-only forward.

A bounded unauthenticated `/soap/server_sa/` matrix then produced:

- `ParentalControl:1#Authenticate`: HTTP 200; service remained healthy;
- `DeviceConfig:1#SOAPLogin`: HTTP 200; service remained healthy;
- `DeviceInfo:1#GetInfo` with 0, 64, 96, 100, 112, 128, 160, 256, 512, and
  1,024 bytes of inert body padding: HTTP 200 in every case;
- a fresh HTTPS control succeeded after every SOAP request;
- no fatal-signal marker, daemon exit, or request-controlled command marker
  was observed.

An initial single-attempt health check failed after the zero-padding GetInfo
case, but a clean reproduction with bounded retry controls passed the complete
matrix. It is therefore not evidence of a daemon DoS.

This dynamic result confirms reachability of the proprietary SOAP handler but
does not confirm the previously suspected body-copy impact. It also does not
turn the two expected public authentication operations into authentication
bypasses by themselves.

The matrix was then extended through 2,048, 4,096, 8,192, and 16,384 bytes of
inert `GetInfo` padding. Every case returned the same 555-byte HTTP 200 response
and passed the post-request health control. Three marker-only command-flow
checks were also sent through `NewNTPServer1`, `NewFirmwareURL`, and the Ookla
server ID. The interposed `system()`/`popen()` monitor observed no marker
reaching a command sink, and the daemon remained healthy after every case.

## 2026-07-24 focused follow-up

The RAX30 methodology was repeated against the exact RAX54S `upnpd` in a
privileged, `--network none` container with a synthetic `br0` and initialized
ACOS NVRAM.

- The unauthenticated WANIPConnection control remained healthy throughout.
- `DeviceInfo:1#GetInfo` sent to `/Public_UPNP_C3` returned the same SOAP 500
  fault for inert padding from 0 through 1,024 bytes; `upnpd` remained alive.
- `/soap/server_sa` returned HTTP 404 from `upnpd`. That URI is present in
  `/usr/sbin/httpd`, while the public firmware descriptor identifies
  `/Public_UPNP_C3` as WANIPConnection only. The unchecked body copy recovered
  in `FUN_000599dc` must therefore not be described as proven public-UPnP or
  unauthenticated reachability without a working `httpd` path.
- The RAX30 GENA callback-parser reproducer was tested on
  `/Public_UPNP_Event_1`. Both an explicit-port callback and a valid callback
  without a port returned HTTP 200, and the daemon remained alive.
- Callback paths of 64, 128, and 256 bytes returned HTTP 200; 512 through 4,096
  returned HTTP 400; 8,192 and 16,384 reset the individual connection. The
  daemon passed a fresh liveness request after every case.

This follow-up does not confirm unauthenticated DoS or RCE. It rejects direct
transfer of the RAX30 callback null dereference to RAX54S and narrows the
strongest remaining lead to the `httpd`-served private SOAP path, whose complete
startup environment is still required for dynamic reachability testing.

## Result

No unauthenticated remote-code-execution path or service-level denial of
service was confirmed in this pass.

This is a negative result for the tested surfaces and inputs, not a claim that
the firmware is free of vulnerabilities. Both the UPnP daemon and proprietary
HTTP/SOAP daemon were reviewed statically. UPnP reached a stable live test
state. The exact HTTP daemon was brought substantially farther under
full-system ARM emulation, but its request worker crashed during startup before
a stable request/response test state was available.

## Static HTTP/SOAP analysis

The exact `usr/sbin/httpd` exposes
`/soap/server_sa/` and imports `system`, `popen`, `doSystem`, `SYSTEM`,
`strcpy`, `strcat`, and `sprintf`. An exhaustive decompile receipt produced:

- functions discovered/attempted/succeeded: 566/566/565;
- failed functions: 1; timed-out functions: 0;
- retries: 2;
- function-local source/sink candidates: 19;
- candidates containing a recovered route: 0;
- candidates containing an authentication marker: 0.

The most concerning automated hit was `FUN_00066fb4`, because it contains both
`recv()` and `system()`. Manual decompilation showed that its `system()` calls
use fixed firmware strings and execute before the receive loop. Received bytes
are copied into a heap allocation only while the accumulated length remains
below the allocation size, then passed to another parser. It is not a
request-to-command flow.

The other command-bearing candidates use fixed strings, NVRAM state, or data
read from local command-output/configuration files. Some are independently
risky shell construction patterns, but this review found no unauthenticated
HTTP/SOAP route feeding those values. In particular, string co-location alone
is insufficient to claim RCE.

The single failed decompilation means the receipt is formally partial rather
than exhaustive-success. Route-specific audits still recovered the
`/soap/server_sa/` gate (`FUN_0002b594`) and `SOAPAction:` parser
(`FUN_0009b658`); neither contained a direct command sink.

## Full-system HTTP validation

The exact daemon and libraries were staged into an ARM initramfs and booted
with an ARM kernel under QEMU. The lab had restricted user-mode networking and
redirected firmware command execution to marker files.

An initial no-argument launch briefly bound `10.0.2.15:9443` and IPv6 port 80,
then faulted at address zero without receiving a request. Fatal-register
capture mapped the fault to PIE offset `0x241a0`:

```text
ldr r1, [r7, #3272]
ldrsb r3, [r1]
```

The NULL value was the certificate-path global. The binary's displayed
`usage: [-S] [-E certfile]` is incomplete: its option parser recognizes `-E`
only when followed by the exact pair `/usr/sbin/ca.pem`
`/usr/sbin/httpsd.pem`. An arbitrary certificate path, or no arguments, leaves
the pointer NULL even though startup later dereferences it.

The lab now stages a generated certificate and key at those embedded paths,
launches `httpd -S -E /usr/sbin/ca.pem /usr/sbin/httpsd.pem`, restores the
firmware's `OPENSSL_CONF=/etc/ssl/openssl.cnf`, and models the empty
ACOS NAT/firewall table at its vendor API boundary. The exact daemon then
retained PID 122 and returned `HTTP/1.0 200 OK` to two TLS control requests
twenty seconds apart. No fatal signal or daemon-exit marker occurred.

The former startup NULL dereference was therefore a resolved emulation launch
contract error, not an unauthenticated remote DoS. No request-controlled
command marker was created.

A subsequent bounded unauthenticated corpus exercised the live TLS service
with a control request after every candidate. It covered:

- `Authenticate` and `SOAPLogin`;
- command-marker values in NTP, firmware URL, and Ookla server fields;
- `GetInfo` body padding through 16 KiB;
- `SOAPAction` values through 64 KiB;
- 16 KiB `Host`, `X-Forwarded-For`, and request paths;
- a 64 KiB malformed XML body; and
- conflicting `Content-Length` headers.

The command-marker shim observed no marker reaching `system()` or `popen()`.
The daemon returned HTTP responses through the 16 KiB boundaries. It closed
the individual connection without a response for the 64 KiB `SOAPAction` and
XML-body cases, but the immediate HTTPS control remained healthy. No fatal
register capture, persistent PID loss, command execution, or service
termination occurred.

## Residual uncertainty

A physical RAX54S is still required for the highest-confidence validation.
The improved full-system lab now supports bounded testing of the proprietary
SOAP handler, but complete vendor flash state and hardware services remain
necessary before attributing behavior that depends on those components. The
evidence currently supports "not confirmed," not "impossible."

## Disposition

- Confirmed unauthenticated RCE: **no**
- Confirmed unauthenticated service DoS: **no**
- HTTP startup failure: **resolved by reproducing the exact certificate launch contract**
- UPnP per-connection malformed-input disruption: **yes**
- Zero-day claim justified: **no**
