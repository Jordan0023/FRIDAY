# RAXE500 UPnP XML record overflow investigation

## Verdict

**Rejected as a demonstrated zero-day:** `sa_parseRcvCmd` contains an unsafe
copy into a fixed-stride command record, but dynamic breakpoints show that
standard UPnP `AddPortMapping` requests do not call this parser. The earlier
claim that `NewPortMappingDescription` reaches this copy was incorrect.

The routine is used by a separate NETGEAR command-dispatch path retained in
the binary. The extracted RAXE500 build does not register `/soap/server_sa`,
and moving its listener from 56688 to 5000 did not make that route reachable.
Without a reachable caller, this is not evidence of an exploitable zero-day.

## Target

- Product: NETGEAR RAXE500
- Firmware: `1.2.13.100_2.0.54`
- Binary: `usr/sbin/upnpd`
- Binary SHA-256: `2bb770f22750fb46974eadd025f9b4289973c6a65298630b3bb5b71624c92848`
- Architecture: ARM 32-bit PIE
- Exposure: LAN HTTP/UPnP service. The isolated daemon selected TCP port
  `56688`; firmware strings also identify the NETGEAR SOAP listener.

## Static data flow

The main UPnP loop at `0x1f89c` accepts TCP connections and receives a bounded
HTTP request into an approximately 0x2000-byte buffer. It parses
`Content-length` and passes the complete request to the command-processing
path.

The XML parser at `0x2dd88` (`sa_parseRcvCmd` in embedded diagnostic strings)
locates the SOAP body and matches element names against a command table. For
each matched value it calculates a record destination as:

```text
record = command_records + (record_index * 0x4c)
value_destination = record + 4
```

At `0x2e234` it obtains the decoded value length with `strlen`. At `0x2e24c`
it performs the equivalent of:

```c
memcpy(record + 4, decoded_value, strlen(decoded_value));
```

There is no comparison against the 0x4c record stride before this copy. A
value longer than the available record payload overwrites the following
record's type, value, and parser metadata. The parser permits up to 20 records,
making adjacent-record corruption deterministic.

After parsing returns, the caller at `0x4b1a0` invokes the large action
dispatcher at `0x438bc` (`0x4b1b8`). Consequently, corruption occurs before
the action is dispatched or any action-specific session requirement can reject
the request.

The dispatcher contains standard unauthenticated UPnP fields including:

- `AddPortMapping`
- `NewInternalClient`
- `NewPortMappingDescription`
- `NewInternalPort`
- `NewExternalPort`
- `NewProtocol`

It also contains separate NETGEAR SOAP login and `sess_id` logic. Those later
markers do not protect the generic parser copy described above.

## Impact assessment

The immediate primitive is an out-of-bounds write into adjacent command
records. Expected first impact is a reliable crash of `upnpd`. Depending on
the allocation location and corrupted record use, control-flow impact may be
possible but has not been established.

The binary has NX stack, PIE, stack canaries, full RELRO, and immediate symbol
binding. These mitigations raise the bar for code execution but do not prevent
heap/global record corruption or denial of service.

## Isolated emulation result

The exact root filesystem was copied to a disposable chroot and `upnpd` was
run under `qemu-arm-static` in a privileged Docker network namespace. A dummy
`br0` at `192.168.1.1/24` allowed the daemon to bind TCP `192.168.1.1:56688`.
No host port was published and no external target was contacted.

The unmodified daemon exits while joining its SSDP multicast group because
the firmware's NVRAM/shared-memory service is absent. For reachability testing
only, the disposable binary's `setsockopt` PLT entry was replaced with a
success-return stub; the XML parser and request handlers were not modified.
This kept the service alive and generated `/tmp/upnp_xml`, whose advertised
WANIPConnection endpoint is `/Public_UPNP_C3`.

Benign descriptor requests returned HTTP 400. SOAP requests to both the
advertised `/Public_UPNP_C3` route and NETGEAR's `/soap/server_sa` route
returned HTTP 404 for values from 16 through 1600 bytes, while the daemon
remained alive. This means the requests were rejected by route lookup before
`sa_parseRcvCmd`; it is not evidence that the unchecked copy is safe. Repeated
`shmget(0x11223350, 0x80000, ...) = ENOENT` calls in the trace explain the
missing runtime control-table registration.

Follow-up work identified the firmware-native solution: `/bin/acos_nvram init`
creates the correct SysV segment and semaphore. Setting `lan_ifname=br0`,
`lan_ipaddr=192.168.1.1`, and `upnp_turn_on=1` then makes the unmodified daemon
serve both device descriptors and emit SSDP advertisements. The reusable
launcher is `scripts/emulate_raxe500_upnp.py`; it uses a disposable rootfs,
publishes no host ports, and probes from a synthetic `192.168.1.2` client
inside the isolated container.

### Fault attribution and parser reachability

The original 16-byte `AddPortMapping` disconnect was reproduced under
`qemu-arm-static -strace`. It was a SIGSEGV at `0x00015203` immediately after:

```text
shmget(0x11223353, 474104, 0666) = ENOENT
shmat(-1, 0, 0) = EINVAL
SIGSEGV si_addr=0x00015203
```

Creating a zero-initialized `0x11223353` NAT runtime segment removed that
fault. The same exact daemon then returned HTTP 200 for description lengths
16, 64, 72, 75, 76, 77, 80, 96, 128, 256, 512, 1024, and 1600. A 2048-byte
value produced a handled HTTP 500, and the listener remained alive.

An ARM GDB breakpoint at `0x2dd88` (`sa_parseRcvCmd`) and at the suspected copy
site `0x2e24c` did not fire for any `AddPortMapping` request. It also did not
fire for NETGEAR `SOAPLogin` or `ParentalControl#Authenticate` requests sent to
the advertised control routes. The binary contains no `soap/server_sa` path
string, returns HTTP 404 for that path, and normally binds only 1900/UDP and
56688/TCP. A disposable patch changing the TCP listener to port 5000 still
returned 404 without reaching the parser.

Therefore increasing `NewPortMappingDescription` does **not** demonstrate
adjacent 0x4c-byte record corruption. The unsafe routine may be dead code or
reachable only through unavailable product-specific initialization, but the
network attack path proposed in this report has been falsified.

### Direct-caller closure

Whole-binary cross-reference recovery identified four direct calls to
`sa_parseRcvCmd`, at `0x497d4`, `0x4acc8`, `0x4b1a4`, and `0x4b330`. They are
conditional branches within the same large product/action dispatcher, not four
independently registered network endpoints. The branches select internal
product/action modes before converging on the same parser and later action
dispatcher. This explains why static cross references outnumber the routes
seen dynamically, but it does not provide an alternative listener or URL.

The earlier network conclusion therefore remains unchanged with higher
confidence: every direct parser caller is now accounted for inside the same
dispatcher cluster, while the exact emulated RAXE500 registration table does
not expose a request path that reaches any of them.

The loopback-only driver in
`pocs/raxe500_upnp_record_probe.py` reproduces the bounded request series. Its
default maximum is 2048 bytes and it refuses non-loopback destinations unless
the operator explicitly opts in.

## Conditions for reopening

Reopen this finding only if a supported RAXE500 configuration exposes a route
that hits the `0x2dd88` breakpoint. Validation must first show an ordinary
request reaches `sa_parseRcvCmd`, then compare record memory before and after a
bounded oversized value. `AddPortMapping` is not a valid reproducer for this
routine. Until such a caller is identified, the finding remains rejected.

## Suggested fix

Reject a decoded value whose length is greater than the destination record's
payload capacity. Replace the raw `memcpy` with a size-aware copy that always
terminates the destination, and reject requests containing more records than
the allocated table supports. Apply equivalent bounds in the later dispatcher,
which also contains multiple unbounded `strcpy` operations into 0x400-byte
value slots.
