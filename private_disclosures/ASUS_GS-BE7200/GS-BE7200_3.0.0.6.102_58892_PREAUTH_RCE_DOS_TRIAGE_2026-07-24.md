### Latest-production verification

On 2026-07-24, ASUS's live global support API returned
`3.0.0.6.102_58892`, released 2026-05-07, as the newest production firmware
for **ROG Strix GS-BE7200**. The separately listed GS-BE7200X is a different
model and firmware line.

The package used throughout this report is the official API-listed
`FW_GS-BE7200_300610258892.zip`:

```text
SHA-256 1e0cff6743b3556f35922e16cf7725fae8178beac9af37f99cbd3f43029a147e
Size    54,675,043 bytes
```

Therefore, the genuine-`httpd` and genuine-`rc` worker-exhaustion test below
already targets the latest production GS-BE7200 firmware available from ASUS
on the test date.

This pass applied the RAX30/EX2800 process without assuming that NETGEAR
implementation details transfer to ASUS: authentication-first route mapping,
command-sink review, adjacent-version comparison, exhaustive decompilation,
and an attempt to construct a network-isolated genuine-binary lab.

## Static coverage

The image contains AArch64 musl executables. Ghidra decompiled every discovered
function in the two primary pre-authentication network services:

| Binary | Functions | Failures | Candidate functions |
| --- | ---: | ---: | ---: |
| `/usr/sbin/httpd` | 774 | 0 | 151 |
| `/usr/sbin/miniupnpd` | 173 | 0 | 14 |

The `httpd` imports `system`, `popen`, `_eval`, `strcpy`, and `sprintf`.
Focused pseudocode review covered every function locally correlated with
`system` or `popen`. The strongest apparent command path is the legacy
`syscmd.sh`/`SystemCmd` facility: it stores a command in a global buffer and
passes that buffer to `system`. Route-table review places the corresponding
diagnostic/apply functionality behind the authenticated handler set. No
pre-authentication route-to-command flow was established.

Other command sinks reviewed were fixed diagnostic commands or commands
constructed from internal/NVRAM state. They are security-sensitive after
authentication but do not establish an unauthenticated RCE.

The complete `miniupnpd` decompilation contains no `system`, `popen`, `_eval`,
`strcpy`, or `sprintf` candidate correlation. The principal network parser
uses bounded `memcpy` operations in the reviewed decompilation. This rejects a
direct code-level transfer of the EX2800 command-injection chain and provides
no static support for the RAX30 callback crash, but it is not a substitute for
dynamic parser testing.

## Dynamic validation status

A full-system AArch64 lab was completed after Greenhouse's root-selection
heuristic rejected this image. The replacement lab uses:

- `qemu-system-aarch64` with an Ubuntu 5.15.0-186 ARM64 kernel;
- a minimal static-ARM64 initramfs that loads `virtio_blk` and switches to a
  1.6 GiB ext4 copy of the genuine firmware root;
- the matching Ubuntu ARM64 modules for virtio networking, bridge, conntrack,
  NAT, and iptables;
- separate QEMU user-network backends for LAN and WAN, both with
  `restrict=on`;
- loopback-only forwards for genuine `httpd`, `miniupnpd`, and `infosvr`,
  including UDP SSDP, NAT-PMP/PCP, and ASUS discovery paths; and
- Greenhouse's ARM64-musl NVRAM compatibility library and ASUS defaults.

The NVRAM compatibility library requires both `/gh_nvram.ini` and a writable
`/gh_nvram/` directory. With those present, both genuine services passed
controls:

- `httpd`: `HTTP/1.0 200 OK`;
- `miniupnpd`: `HTTP/1.1 200 OK`.
- `infosvr`: remained live while bound to LAN UDP port 9999.

The bounded security matrix covered:

- six unauthenticated/authentication-adjacent HTTP routes;
- a harmless unauthenticated `SystemCmd` marker canary;
- `Host` values through 65,536 bytes;
- paths through 16,384 bytes;
- duplicate and negative `Content-Length` cases;
- the RAX30-shaped GENA callback and callback values through 16,384 bytes;
- 4,096-byte `SID`, `TIMEOUT`, and `NT` values; and
- a SOAP port-mapping description containing a harmless command canary.

Every case was followed by a fresh control request. Both genuine daemons
remained alive through the complete matrix. Neither command canary created the
guest marker. The 16,384-byte HTTP path and negative `Content-Length` received
HTTP 400; malformed GENA renewal headers received HTTP 412; the SOAP canary
received HTTP 500.

### Extended stateful and UDP validation

The lab was then expanded into the remaining strongest LAN-facing areas:

- five SSDP cases: valid root-device and `ssdp:all` searches, duplicate `ST`,
  a 4,096-byte `ST`, and a 1,024-byte binary datagram;
- a valid guest-internal GENA lifecycle with callback delivery: new
  subscription, SID renewal, and unsubscribe all returned HTTP 200;
- host-side invalid GENA transitions, including unknown SID, mixed
  new-subscription/renewal headers, and renewal after removal;
- six NAT-PMP cases covering public-address, TCP/UDP mapping, version,
  truncation, and a 1,024-byte datagram;
- six PCP cases covering ANNOUNCE, MAP, version, truncation, malformed options,
  and a 1,024-byte message; and
- 61 `infosvr` cases: valid opcode 31, the historical opcode-51 command
  packet, truncation boundaries, opcodes 29 through 55 plus `0xffff`,
  declared command-length boundaries through `0xffff`, and header variants.

QEMU slirp did not route UDP replies back through these forwards, but this did
not prevent parser validation. The genuine miniupnpd serial log records the
SSDP searches and every NAT-PMP/PCP request, including MAP and option parsing.
The genuine `infosvr` syscall trace records exactly 61 `recvfrom` calls, one
per matrix case. It records no child `execve`; the historical opcode-51 packet
created no marker.

All three daemons remained alive. The final miniupnpd HTTP control succeeded,
`infosvr` remained alive, and `command_marker_present=false`. Repeat boots
also passed after the harness was hardened to remove stale daemon PID files.
No unauthenticated RCE or DoS was reproduced in these extended areas.

### Hardware-adjacent layer-2 validation

A third virtio NIC was connected only to a localhost UDP socket-netdev tunnel.
This permits complete Ethernet-frame injection without a host TAP device,
privileges, or contact with a physical network. The genuine firmware
`lldpd` was run receive-only on that interface under syscall tracing with
LLDP, CDPv1/v2, EDP, and FDP enabled.

The lab supplied the firmware-expected `/sbin/lldpcli` symlink and standard
privilege-separation account entries. The first diagnostic run caught and
corrected an administratively paused daemon; only the subsequent unpaused
decoder run is treated as evidence.

The final bounded matrix contained 30 sends:

- valid LLDP controls before, between, and after malformed groups;
- runt Ethernet, empty LLDP, one-byte and overclaimed TLV headers;
- missing, duplicate, empty, short, and oversized mandatory fields;
- short capabilities, management-address, and organizational TLVs;
- 511-byte unknown and system-name TLVs;
- wrong destination and a bounded 4,096-byte jumbo attempt;
- a minimal CDPv2 control; and
- CDP version, 802.3 size, TLV length, address, and native-VLAN boundaries.

The virtio NIC discarded the 13-byte runt and 4,096-byte jumbo before the
daemon. The other 28 frames are recorded as AF_PACKET receives. Debug evidence
records 13 LLDP and eight CDPv2 decoder entries and the expected reject
branches, including TTL, capabilities, management-address, organizational,
unknown TLV, frame-size, TLV-length, address, and VLAN validation. Valid LLDP
sentinels were decoded after both malformed groups.

`lldpd` remained alive and its trace contains no `SIGSEGV`, `SIGABRT`,
`SIGBUS`, or `SIGILL`. No concrete anomalous branch suitable for deeper
coverage-guided reproduction emerged from this matrix.

### Authentication-dispatch and `netool.cgi` follow-up

An authentication-first reconstruction of the `httpd` route table identified
the explicit pre-authentication exemption table separately from the larger
handler table. This corrected an earlier ambiguity: `apply.cgi`,
`cfg_onboarding.cgi`, `findasus.cgi`, `check_Auth.cgi`, `netool.cgi`, and
`appGet.cgi` are not members of the exemption table.

A 29-case full-system probe covered the genuine pre-authentication
`page_default.cgi`, `QIS_default.cgi`, and token handlers, with authentication
controls for those six non-exempt routes. Quote, scheme-relative, JavaScript
scheme, oversized, and CRLF canaries did not establish reflected XSS, open
redirect, memory corruption, or service failure. Empty token requests returned
error states and all liveness controls passed.

The dispatcher nevertheless continues into selected handlers after emitting
its authentication redirect. Exact raw responses contain two HTTP status
lines on one connection:

- `cfg_onboarding.cgi`: login/page redirect followed by the onboarding
  handler's meta refresh;
- `check_Auth.cgi`: redirect followed by `{"asus_auth":"OK"}`; and
- `netool.cgi`: redirect followed by `{"successful":"0"}`.

Each first response specifies `Connection: close` and has no `Content-Length`.
This makes classic cross-request response desynchronization unlikely in the
direct-router deployment. The important result is instead confirmed
unauthenticated execution of these nominally authenticated handlers.

The `netool.cgi` output handler at `0x00433de4` reads attacker-controlled
`type`, `target`, and other network-test parameters. It calls the firmware's
input blacklist, then copies `target` with:

```c
snprintf(target_buffer, 0x80, attacker_target);
```

The attacker input syntactically occupies the format argument and no variadic
arguments are supplied. A first static pass therefore treated this as a
possible uncontrolled-format-string primitive. Instrumented dynamic validation
subsequently disproved reachability of format directives: `%p`, `%n`, and a
high positional specifier were replaced by an empty target before `snprintf`,
while a literal `FRIDAYTARGET` control appeared at offset `0xba` of the exact
328-byte daemon request.

The validator at `0x0045b56c` first calls `check_xss_blacklist`, rejects line
feed, and then permits only alphanumerics, underscore, space, tab, dash, dot,
and colon. Percent is not permitted. There is no later URL decode between the
validator and `snprintf`, and NUL-based parser disagreement would terminate
both operations at the same point. The format-string route is therefore
**not an exploitable primitive under the observed parser and validator**.

The real net-tool implementation resides in the `rc` multicall binary. It
constructs commands for BusyBox `ping`, `traceroute`, and `nslookup`, plus
`netstat` and `netstat-nat`, and passes them to `system()`. Although permitted
spaces and dashes create an option-injection surface, the validator excludes
shell separators, substitution syntax, slash, percent, and line feed. Review
of the exact command constructors did not identify an execution-capable
BusyBox option or a way to introduce a second shell command. This closes the
candidate RCE chain on the tested firmware. Resource-exhaustion through numeric
limits or diagnostic options remained a separate DoS question.

### Confirmed emulated net-tool worker-exhaustion DoS

The lab was extended with a dedicated profile running the genuine `netool_main`
applet from the firmware `rc` multicall binary under syscall tracing. A benign
control generated the expected command:

```text
ping -c 1 -w 1 -q 127.0.0.1
```

The daemon clamps an attempted million-packet `pcnt` to 10, so a single
`target=-f 127.0.0.1` option-injection case did not establish an outage.

A bounded burst of 40 parallel unauthenticated `netool.cgi` requests did
establish a reproducible transient management-plane denial of service:

```text
type=3
target=192.0.2.1
pcnt=1
response=10
exec=10
```

This request selects the repeated blocking-ping path. The HTTP handler sends
each accepted 328-byte request to the daemon, which creates a worker thread;
the worker repeatedly starts BusyBox ping toward the lab's non-responsive WAN
address. Of the burst, the trace recorded 37 complete requests, 43
`CLONE_THREAD` operations, and at least 42 ping `execve` calls.

Most burst requests timed out after eight seconds. More importantly, two
independent `Main_Login.asp` controls timed out after six seconds, and a third
took 5.892 seconds. Subsequent controls recovered to the instrumented
three-to-four-second baseline. The serial health monitor continued reporting
`httpd=alive`, establishing transient resource starvation rather than a daemon
crash.

This is a confirmed unauthenticated availability impact in the full-system
emulation. It is not RCE. Physical-device confirmation must establish that the
post-setup authentication dispatcher has the same handler-continuation
behavior and measure impact without QEMU/strace overhead before this is
represented as a product zero-day.

### WAN-interface reachability

The lab was extended with a second localhost-only QEMU forward directed to the
guest WAN address (`192.0.2.15:80`), separately from the LAN forward
(`10.0.2.15:80`). Both user-network backends remained `restrict=on`.

Traffic arriving through the WAN NIC reached the genuine `httpd`:

- `Main_Login.asp` returned HTTP 200;
- `netool.cgi` produced the same redirect plus second handler response; and
- `check_Auth.cgi` produced the same double-response behavior.

The same 40-request bounded worker burst sent through the WAN forward caused
the first independent WAN and LAN login controls both to time out after six
seconds. The second WAN control remained incomplete after six seconds while
LAN recovered in 0.605 seconds. Trace evidence recorded 37 daemon requests, 41
thread clones, and at least 40 ping executions. This confirms that traffic
which reaches `httpd` on the WAN interface can trigger the global management
DoS.

This does **not** establish factory-default Internet exposure. The lab forwards
directly to the WAN NIC and intentionally does not reconstruct the router's
complete production firewall policy. A normal device is expected to gate WAN
management according to remote-administration/firewall configuration.
Accordingly:

- application-layer WAN reachability: confirmed in emulation;
- WAN-triggered DoS when port 80 is reachable: confirmed in emulation;
- factory-default Internet/WAN exposure: not confirmed.

### Unconditional-WAN chain attempts

All identified prerequisites for converting the conditional WAN result into a
factory-default WAN path were tested or traced:

- A pre-auth `apply.cgi` mutation canary attempted to set
  `misc_http_x=1`; it stopped at the login redirect and did not enter the apply
  handler.
- The same request attempted `fw_enable_x=0`, `restart_firewall`,
  `vts_enable_x=1`, and a virtual-server rule. These mutations were likewise
  authentication-gated.
- Genuine miniupnpd rejected a router self-map
  (`40080 -> 10.0.2.15:80`) with UPnP error 501 `ActionFailed`.
- PCP `THIRD_PARTY` did not create the equivalent map; NAT-PMP is
  source-address-bound.
- Firmware defaults have `ipv6_fw_enable=1`; firewall templates classify
  input by kernel interface and direct non-LAN traffic into the WAN chain.
  QEMU slirp could not host-forward to an IPv6 guest address, so a direct
  dynamic WAN-v6 test was not possible, but no IPv6 firewall mutation or
  classification bypass was found.
- Optional forwarding services did not supply a default chain: WebDAV proxy,
  AiDisk, SSH, and virtual-server forwarding are disabled in the defaults.
  The located lighttpd configuration is the captive portal on port 8083.
- HTTP headers cannot change the firewall's input-interface classification;
  they are parsed only after the kernel WAN gate.

No tested bullet produced unconditional WAN exposure. Detailed evidence is in
`router-agent-results/gs-be7200-triage/unconditional-wan-chain-matrix-2026-07-24.txt`.

## Known-vulnerability boundary

As of 2026-07-24, ASUS has published CVE-2026-13385 for the
3.0.0.6_102 series. It concerns certificate/integrity validation during a
router update and requires a network man-in-the-middle position. It is
published prior art, not a zero-day, and it is not the unauthenticated LAN
HTTP/UPnP RCE/DoS requested here.

Any later claim must also be checked against CVE-2026-11851 and other July
2026 ASUS router bulletins before being described as new.

## Conclusion

No unauthenticated RCE was established. The next-technique pass found a
concrete authentication-dispatch anomaly:
nominally authenticated handlers execute after a redirect. However,
instrumentation showed that the apparent `netool.cgi` format-string path is
neutralized by its allowlist, and review of the downstream `system()` command
constructors found no shell-command injection using the surviving character
set. The current evidence does not support an RCE claim.

The same handler-continuation behavior does expose the genuine net-tool
worker/process path. A bounded parallel request burst reproducibly denied
independent management requests before recovery. This confirms a transient
unauthenticated DoS in the full-system emulator; physical-device confirmation
and prior-art review remain necessary for a zero-day claim.

The full-system lab now covers stateful SSDP/GENA, NAT-PMP, PCP, the
normal-boot ASUS `infosvr` discovery daemon, and genuine LLDP/CDP layer-2
decoding. Physical-device confirmation should still determine whether the
authentication-dispatch behavior persists after normal setup and whether
unbounded diagnostic counts or option injection provide a practical DoS.
