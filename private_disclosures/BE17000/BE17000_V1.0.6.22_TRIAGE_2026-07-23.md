# Private security triage: NETGEAR BE17000 V1.0.6.22

Date: 2026-07-23  
Status: static-analysis candidates; runtime confirmation required

## Scope

- Product firmware label: BE17000 / RS600 series
- Firmware: V1.0.6.22
- Official archive SHA-256: `2a9b10038ea6b9b47f5571d67933104cdd9b57918850c09331bfc7f5e3a1c701`
- Root filesystem: SquashFS at image offset `10257620` (`0x9c84d4`)
- Analysis was offline. No internet-exposed router was probed.

## Result

No unauthenticated RCE is confirmed.

Two unauthenticated LAN-reachable MiniUPnPd parser defects are credible DoS
candidates. A third, more serious upstream heap overflow was investigated and
is probably not compiled into this firmware.

## Rejected DoS candidate: empty SOAPAction

The firmware ships:

`miniupnpd 2.2.0-RC0 RS300-V1.0.6.16-584eeee Mar 16 2026`

Upstream commit `f56bd09b2f2650126b832c5f30a65a09e28167fa`, dated
2026-03-23, added a missing `n >= 2` check before examining `p[n-1]` while
removing quotes from the `SOAPAction` HTTP header.

The firmware build predates that fix and exposes the affected SOAP parser over
UPnP without authentication. Further source review showed that when the parsed
value length is zero, `p[-1]` still points inside the allocated HTTP request
buffer (normally at the colon or whitespace preceding the value). This is a
logical parsing defect, but it is not an allocation-boundary violation and is
not expected to crash the daemon. Do not report it as a DoS without contrary
runtime evidence.

## Candidate 2: truncated XML out-of-bounds read

Upstream commit `3cfb4fb78d5ac04ed0dadc8dd842fc9e448916db`, also dated
2026-03-23, added an end-of-buffer check after parsing `=` in an XML attribute.
The upstream regression input was:

`<element attribute=`

The BE17000 MiniUPnPd build predates the fix and its SOAP actions use the same
MiniXML parser. A request body terminating immediately after `=` can read past
the declared body.

An AddressSanitizer build of the vulnerable upstream parser confirmed a
one-byte heap-buffer-overflow read at `minixml.c:66` for an exactly sized
19-byte allocation containing this input. The reproducer is
`harnesses/minixml_truncated_asan.c`.

Observable router DoS is not yet confirmed. MiniUPnPd's production receive
buffer may have spare capacity after the declared HTTP body, in which case the
invalid read remains inside the allocation and does not fault. A bounded
hardware test should use the exact Content-Length, send one request, and verify
whether MiniUPnPd crashes or is restarted. Repeated traffic is unnecessary and
should not be used.

### Firmware emulation result

The genuine firmware `/usr/sbin/miniupnpd` was run under qemu-arm in a
network-disabled Docker namespace using the extracted V1.0.6.22 libraries.
Only firewall bookkeeping and qemu-user's incompatible multicast `setsockopt`
were shimmed; HTTP, SOAP, and MiniXML parsing remained in the firmware binary.

- Baseline `/rootDesc.xml`: HTTP 200; daemon remained listening.
- Exact 19-byte `<element attribute=` body: HTTP 500; daemon remained listening.
- Empty `SOAPAction`: HTTP 500; daemon remained listening.

Neither candidate produced an observable DoS in this emulation. The XML
one-byte invalid read remains a confirmed memory-safety defect under ASan, but
current evidence does not support reporting it as a BE17000 denial of service.
Physical-hardware behavior could still differ because of allocator layout.

The reusable controller is `scripts/emulate_be17000_upnp.py`.

### Extended malformed-request corpus

A second run exercised 35 bounded cases against the genuine firmware daemon:

- 18 truncated XML states around elements, attributes, quotes, comments, CDATA,
  declarations, and nested SOAP elements
- 9 empty, unterminated, and 1-16 KiB `SOAPAction` values
- 6 negative, nonnumeric, hexadecimal, signed, and very large Content-Lengths
- a 16 KiB header and 64 KiB body

Every case was followed by a fresh `/rootDesc.xml` health request. All 35
health checks succeeded, the process remained present, and TCP port 56688
remained listening. The two very large Content-Length cases returned no
application response within the bounded timeout but did not wedge or terminate
the daemon.

Result: no unauthenticated DoS reproduced.

### Process-execution/RCE review

Focused Ghidra analysis found one caller of `popen()` and no request-reachable
caller of `execve()`. The `popen()` caller passes a constant command used for
the firmware's port-conflict check; its four parameters are written to a file
with a bounded/static format and are not incorporated into the shell command.
No SOAP/HTTP value-to-process-execution path was established.

Result: no unauthenticated RCE path found in the emulated MiniUPnPd surface.

## Rejected lead: PinholeVerification heap overflow

Upstream commit `b24d59571a4d83566dc73b5c31df293ab9cab2da` (2026-06-10)
fixed a heap overflow in `PinholeVerification()`. Although the firmware's
nominal MiniUPnPd version predates the fix, its binary does not contain
`AddPinhole`, `UpdatePinhole`, `CheckPinholeWorking`, `GetPinholePackets`, or
other IPv6 pinhole action strings. The affected feature therefore appears to
be compiled out and should not be reported for this product without contrary
runtime evidence.

## Web administration surface

`/usr/sbin/net-cgi` is a 1,272,404-byte ARM PIE, runs through Lighttpd as root,
and handles every web path. It imports `system`, `popen`, `execve`, `execl`,
`strcpy`, and `sprintf`. It contains explicitly unauthenticated routes including
`unauth.cgi`, `currentsetting.htm`, `genie.cgi`, and SOAP handlers.

Focused decompilation traced the route dispatcher, authentication exceptions,
and direct process-execution callers. The reviewed `system()` call in the main
dispatcher uses a constant command, and no request-controlled unauthenticated
path to a shell sink was established. This remains a high-value fuzzing target,
not an RCE finding.

### Full-system net-cgi emulation

The earlier runtime blocker was resolved with a full-system ARM guest:

- the genuine firmware `/bin/smd` starts and exposes
  `/var/smd_messaging_server_addr`
- the genuine Lighttpd 1.4.45 executable listens on guest TCP 80
- all files are dispatched through the genuine root-running
  `/usr/sbin/net-cgi`
- QEMU networking uses `restrict=on` and forwards only host loopback TCP 26180

The firmware archive does not contain the writable datalib configuration
partition or the device-specific encrypted TLS storage. The lab therefore uses
an HTTP-only Lighttpd wrapper and a narrowly scoped `config_*` shim representing
an initialized router with remote management disabled. Authentication logic,
route exceptions, request parsing, CGI/SOAP handlers, and process sinks remain
in the firmware binary. SSK automatic startup is disabled because it requires
physical board/flash services and is not required for SMD messaging.

Runtime baselines succeeded:

- unauthenticated `GET /currentsetting.htm`: HTTP 200 with RS600/V1.0.6.22 state
- unauthenticated SOAP `DeviceInfo#GetInfo`: HTTP 200 with an RS600 response
- an uncredentialed Genie CGI request: HTTP 401

A 22-case malformed SOAP regression then exercised truncated XML states,
deeply nested XML, an 8 KiB attribute, a 64 KiB body, malformed and 4 KiB
SOAPAction headers, duplicate/negative Content-Length values, and a 16 KiB
header. Every case was followed by `GET /currentsetting.htm`; all 22 health
checks succeeded. Framing errors were rejected with HTTP 400 or 431.

Result: the net-cgi runtime-emulation limitation is resolved. No DoS was
reproduced in the initial regression.

## AFC mobile-app service

The firmware's genuine `/usr/sbin/afcmd` was booted in a full-system ARM VM
using the extracted firmware libraries and a real ARM Linux kernel. The daemon
bound its HTTPS service on TCP 19603 and registered `/info`, `/challenge`,
`/pair`, `/pairings`, `/unpair`, and `/location`. Host access was restricted to
the loopback-forwarded test port and QEMU user networking was configured with
`restrict=on`.

The firmware archive omits the device-unique TLS private key. A disposable
lab-only certificate/key pair was therefore supplied at the TLS boundary. AFC
routing, preprocessing, authentication, JSON parsing, and endpoint handlers
remained the genuine firmware code.

A bounded campaign sent 57 malformed requests:

- ten malformed JSON bodies to each of five state-changing/query routes
- deeply nested JSON, invalid Unicode, binary bytes, and a 4 KiB field
- an overlong method, 8 KiB path, and 16 KiB header
- duplicate and negative Content-Length values
- a truncated chunked body and an 8193-byte body above AFC's configured
  8192-byte maximum

Every case was followed by a fresh unauthenticated `/info` health request.
All 57 health checks succeeded. Requests rejected at the HTTP framing limit
often returned no application response, but the daemon continued serving
subsequent TLS requests. The serial log contained expected JSON/authentication
errors and no assertion, abort, stack failure, segmentation fault, or daemon
exit.

Exhaustive Ghidra coverage decompiled all 306 discovered AFC functions with no
failures. No function-local request-source/process-execution correlation was
found. The binary imports `popen`, but no unauthenticated request-to-process
execution flow was established.

Result: no unauthenticated AFC RCE or DoS reproduced.

## Runtime confirmation plan

1. Use a BE17000/RS600 owned by the tester, disconnected from production.
2. Record firmware version, MiniUPnPd PID, uptime, and service logs.
3. Send one empty-`SOAPAction` request to the LAN UPnP HTTP port.
4. Check response, process survival, restart, and router availability.
5. Repeat from a clean boot with one truncated-attribute XML request.
6. Preserve packet capture, request bytes, logs, and timestamps.
7. If a crash occurs, repeat once only and collect a core dump or debugger trace.
8. Privately disclose confirmed behavior to NETGEAR before publishing details.

The single-request helper `harnesses/be17000_upnp_single_shot.py` discovers the
target's advertised control URL, sends exactly one selected probe, and performs
one UPnP availability check. It requires an explicit target and the
`--i-own-this-router` acknowledgement.

## Confidence

- Affected code lineage: high
- Unauthenticated LAN reachability: high
- XML memory-safety defect: confirmed in an instrumented vulnerable build
- Observable BE17000 DoS: not reproduced in genuine-daemon emulation
- RCE: unsubstantiated
