# GL-MT5000 4.9.0 hybrid full-system WAN result

Date: 2026-07-24

## Scope and fidelity

This was an isolated QEMU experiment. It used the genuine GL-MT5000 4.9.0
AArch64 root filesystem and userspace with an official OpenWrt 22.03.7
`armvirt/64` Linux 5.10.221 kernel and matching generic netfilter modules.

This is a hybrid full-system environment, not MT7987 hardware emulation. QEMU
does not provide an MT7987 machine, while the genuine Linux 5.4.281 kernel
lacks the QEMU `virt` PL011 and virtio drivers required to boot that machine.

## Network layout

- `eth0`: isolated LAN, `192.168.8.1/24`
- `eth1`: isolated WAN, DHCP/DHCPv6
- QEMU user-mode networks were separate.
- Host exposure was bound only to `127.0.0.1`.
- No public or third-party address was probed.

## Dynamic observations

The genuine GL.iNet Nginx started and listened on TCP 80 and 443 on IPv4 and
IPv6. The genuine firewall scripts populated IPv4 and IPv6 netfilter tables.

The IPv4 `INPUT` chain dispatched:

- `eth0` to `zone_lan_input`
- `eth1` to `zone_wan_input`

The WAN input chain allowed UDP destination port 68, ICMP echo, IGMP,
established connections, and DNAT traffic. Remaining traffic entered
`zone_wan_src_REJECT`. There was no default TCP 80 or TCP 443 accept rule.

With the same Nginx listener active:

- LAN path: HTTP 200, 749-byte body.
- WAN path: five-second timeout, zero response bytes.

The genuine BusyBox `udhcpc` previously completed a DHCPv4 discover/select/
lease exchange on the isolated WAN and received `192.0.2.15` for 86400
seconds.

After IPv6 was explicitly re-enabled on the WAN interface, the genuine
`odhcp6c` process remained alive during the bounded observation window. The
GL.iNet hotplug environment otherwise disabled IPv6 in this generic-machine
boot. This run did not provide a controlled DHCPv6 server capable of injecting
malformed responses, so it does not dynamically prove or disprove the
previously identified logical out-of-bounds-read candidate.

## Conclusion

The default factory firewall blocks unsolicited WAN access to the management
listener even when Nginx binds all interfaces. The confirmed unauthenticated
WebUI lockout behavior therefore remains LAN-reachable by default and is not
shown to be WAN-reachable by this experiment.

No authentication-free WAN opening, firewall bypass, or second vulnerability
was found. Configured DNAT/remote-management exposure remains conditional on
prior configuration and is not a default WAN path.

## Limitations

- Generic QEMU kernel and NIC drivers replace the MT7987 kernel/driver layer.
- MediaTek switch/NAT offload and board-specific `/proc/gl-hw-info` behavior
  are absent.
- Several board hotplug scripts emitted expected errors and attempted package
  maintenance because the generic machine lacks GL hardware metadata.
- No malformed DHCPv6 responder was connected.
- This result is local research evidence only; no report was submitted.
