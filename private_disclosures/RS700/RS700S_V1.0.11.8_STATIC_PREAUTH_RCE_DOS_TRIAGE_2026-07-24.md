# RS700S V1.0.11.8 static pre-authentication RCE/DoS triage

## Outcome

Static review and bounded user-mode validation did not confirm a new
unauthenticated RCE. The proprietary `upnpd` normalized all accepted
`AddPortMapping` command arguments and remained healthy throughout the
command-injection and malformed-framing corpora.

A separate connection-availability test confirmed that `upnpd` serializes
unauthenticated idle clients: one idle TCP connection temporarily stalls
functional requests, while four and eight queued idle connections produce
approximately 4.5- and 8.5-second response delays. This is a renewable
LAN-adjacent denial of the UPnP service in emulation, not a daemon crash or
demonstrated device-wide outage. Hardware confirmation is still required
before disclosure.

## Public prior art

The closest identified prior issue is CVE-2025-12946. It is command execution
in the RS700 speed-test feature when an adjacent attacker performs DNS
manipulation and a speed test is run. NETGEAR lists RS700 versions through
V1.0.7.82 as affected and V1.0.9.6 or later as fixed:

- https://nvd.nist.gov/vuln/detail/CVE-2025-12946
- https://kb.netgear.com/000070416/December-2025-NETGEAR-Security-Advisory

V1.0.11.8 is newer than the fixed version. Its release note says that this
build fixes a GUI/app speed-test issue, but does not describe a security fix:

- https://kb.netgear.com/000070816/RS700S-Firmware-Version-1-0-11-8

The speed-test shell-command construction observed below must therefore be
treated as adjacent prior art until a distinct input path and security impact
are proven.

## Strongest candidate: proprietary UPnP command construction

`upnpd` imports all of:

- `recv`, `recvfrom`, and `read`;
- `strcpy`, `strcat`, `sprintf`, `sscanf`, and `memcpy`;
- `system` and `popen`.

It parses `SUBSCRIBE`, `UNSUBSCRIBE`, standard SOAP actions such as
`AddPortMapping`, and numerous private NETGEAR actions in one 32-bit ARM
process. Relevant private actions include:

- `SetOOKLASpeedTestStart`;
- `SetFirmware`;
- `SetConfiguration`;
- `SetConfigLAN`;
- `SetRemoteManagementEnable`;
- wireless credential and configuration setters.

Confirmed command templates in the binary include:

```text
arno_nat_cli_new_design pforward_apply_dynamic add %s %s %s %s
arno_nat_cli_new_design pforward_apply_dynamic del TCP %d %d %s
arno_nat_cli_new_design pforward_apply_dynamic del UDP %d %d %s
/usr/sbin/speedtest %s %d
bcm_flasher %s
```

The standard `AddPortMapping` route was the most important unauthenticated
candidate because its command template receives four formatted string fields.
Closer disassembly established that the exact sink is the variadic
`shared_util_doSystem` helper in `libacos_shared.so`, rather than a direct
libc `system` call. The helper is reached only when
`shared_nat_pf_rule_add_dynamic_rule` returns success.

The private speed-test and firmware routes have stronger command effects but
may require NETGEAR SOAP authentication or a valid session. The firmware
handler also appears to stage data under fixed paths such as
`/tmp/image.chk` and `/tmp/image.w`; the observed `bcm_flasher` use is
therefore not by itself command injection.

### Dynamic validation

The genuine ARM daemon was run with QEMU user mode in an isolated Docker
container with no external network. Its generated device description
identified model `RS700`, and its public SOAP control endpoint was reachable
at `/Public_UPNP_C3`.

The 26-case corpus covered independent semicolon mutations in port-mapping
fields; subshell, backtick, and newline description canaries; whitespace
confusion; description lengths through 4096 bytes; GENA callback and timeout
mutations; and three private SOAP actions without authorization.

The emulated NAT backend did not naturally return the success value needed to
reach the command call. A preload shim therefore forced only
`shared_nat_pf_rule_add_dynamic_rule` to return zero and intercepted
`shared_util_doSystem` before execution. Every accepted mapping produced the
same normalized command:

```text
arno_nat_cli_new_design pforward_apply_dynamic add TCP 54321 54321 192.168.1.2
```

None of the canaries crossed the command boundary. Invalid protocol and
internal-client values were rejected with HTTP 500. Description lengths of
2048 and 4096 bytes were handled with HTTP 500. The long GENA callback was
handled with HTTP 400. The genuine daemon retained the same PID and answered a
health check after every case.

The tested private speed-test, firmware, and configuration requests returned
HTTP 404 at `/soap/server_sa`; those routes were not registered on the
emulated public listener.

## Malformed HTTP/SOAP framing validation

The genuine ARM `upnpd` was subsequently exercised with 36 raw-socket cases
against its unauthenticated `/Public_UPNP_C3` listener. The corpus covered:

- LF-only and mixed line endings, a missing header terminator, and truncated
  request bodies;
- negative, signed, nonnumeric, hexadecimal, conflicting duplicate, wrapping,
  and oversized `Content-Length` values;
- `Transfer-Encoding: chunked` combined with `Content-Length`;
- empty, unquoted, unterminated, duplicate, folded, and 8 KiB `SOAPAction`
  headers;
- malformed header lines, an 8 KiB generic header, an 8 KiB URI, and a 1 KiB
  method;
- embedded NUL bytes in a header and URI;
- empty, truncated, NUL-containing, mismatched, 128-level-deep, and bounded
  entity-bearing XML;
- action/body mismatch, bytes after the declared body, and a pipelined second
  request.

Every case was followed over a fresh connection by a functional request for
`/Public_UPNP_gatedesc.xml`. All 36 health checks returned `HTTP/1.1 200 OK`.
The daemon retained PID 105 and continued listening on `192.168.1.1:56688`
after the corpus.

The 8 KiB generic-header, `SOAPAction`, and URI cases reset only their own
connections. Malformed XML returned HTTP 500, while malformed request lines
generally returned HTTP 400 or 404. None caused a persistent service failure.

The parser was permissive in ways that may merit protocol-hardening review:
several invalid or conflicting `Content-Length` forms, duplicate/folded
headers, and chunked-plus-length ambiguity received HTTP 200. On this direct,
unauthenticated UPnP endpoint, that behavior alone does not establish a
security-boundary discrepancy, request smuggling, command execution, or
denial of service.

Evidence:

- `known_firmware/emulation/RS700/rs700_http_soap_framing_probe.py`

## Unauthenticated slow-connection service starvation

The genuine ARM `upnpd` processes accepted TCP clients serially. A bounded
raw-socket probe held connections open without sending request bytes and
issued a functional device-description request from another client.

One idle unauthenticated connection caused the functional request to exceed
the 1.5-second client deadline in three of three trials. Closing the idle
socket restored service on the first recovery request, without restarting the
daemon.

The daemon applies an absolute per-connection timeout: in three extended
eight-second trials, the initial health request timed out, but a request near
the end of the hold succeeded because the daemon had already closed the idle
client. Sending one byte every 750 ms did not defeat this absolute timeout.

Queued connections nevertheless serialize the timeout:

| Idle connections | Trials | Normal baseline | Response while queued |
|---:|---:|---:|---:|
| 4 | 3 | about 1.0 s | 4.507–4.508 s |
| 8 | 3 | about 1.0 s | 8.514–8.515 s |

All trials recovered without a process restart. After testing, the daemon
retained PID 42, used approximately 11.6 MiB RSS, and remained listening on
`192.168.1.1:56688`.

This establishes a low-resource availability attack against the
unauthenticated LAN UPnP service in the user-mode emulation. The linear queue
behavior supports the inference that an attacker can replenish idle
connections to renew the delay. It does not establish a router crash, memory
exhaustion, WAN exposure, or impact on the primary HTTP administration
service. The exact timeout and practical device-wide impact require physical
RS700S validation.

## WAN exposure validation

WAN exposure of the UPnP service-starvation condition was not confirmed.

The isolated lab was rebuilt with distinct interfaces and network segments:

- router LAN: `br0`, `192.168.1.1/24`;
- router WAN: `wan0`, `198.51.100.1/24`;
- external client: `198.51.100.2/24` in a separate network namespace.

With firmware NVRAM set to those LAN and WAN interfaces, the genuine daemon
opened TCP/56688 only on `192.168.1.1`. It did not open TCP/56688 on the WAN
address or a wildcard address. A connection from the external client to
`198.51.100.1:56688` received an immediate connection refusal.

The SSDP UDP/1900 socket did bind to `0.0.0.0`. With no firewall policy
installed, a unicast M-SEARCH from the external client to the WAN address
received `HTTP/1.1 200 OK`; WAN multicast did not receive a response. This
demonstrates that interface binding alone is insufficient to protect SSDP,
although it does protect the TCP service used by the connection-starvation
candidate.

The firmware's default firewall configuration sets `EXT_IF`, enables
`DEFAULT_POLICY_DROP`, and ends firewall construction with explicit IPv4 and
IPv6 INPUT drops for every external interface:

```sh
for interface in $EXT_IF; do
  ip4tables -A INPUT -i $interface -j DROP
  if [ "$IPV6_DETECTED" = "1" ]; then
    ip6tables -A INPUT -i $interface -j DROP
  fi
done
```

Applying the equivalent external-interface INPUT drop in the dual-interface
lab blocked all four external tests: TCP to the WAN address, TCP to the LAN
address routed through the WAN interface, unicast SSDP, and multicast SSDP.
Each reached the two-second client deadline without a response.

The combined evidence rejects default WAN exposure in this model:

- the vulnerable TCP listener is LAN-address-bound;
- the default firmware firewall drops external-interface input;
- the dual-interface lab could not reach TCP/56688 from the WAN segment.

This does not prove every physical-device configuration is safe. Hardware
validation should still check remote-management modes, user-generated
firewall exceptions, IPv6 interface assignment, bridge/AP modes, and whether
startup ordering creates a brief pre-firewall exposure window.

### Higher-value configuration and startup checks

Additional tests did not produce a TCP WAN path.

The lab assigned both IPv4 and global IPv6 addresses to distinct LAN and WAN
interfaces and enabled the representative IPv6 NVRAM flag. Under each tested
mode, `upnpd` opened only:

```text
tcp 192.168.1.1:56688
udp 0.0.0.0:1900
```

It did not open TCP/56688 on the WAN IPv4 address, `0.0.0.0`, a LAN IPv6
address, a WAN IPv6 address, or `[::]`.

The same listener set was observed under:

- default router flags;
- remote management enabled on port 8443;
- representative AP-mode flags;
- representative bridge/extender flags.

Remote management therefore changed no `upnpd` binding in this bounded test.
AP and bridge modes also did not create a second externally bound listener;
on physical hardware these modes may reclassify a former WAN port as part of
the trusted LAN, which is not Internet-side WAN exposure.

Static inspection found ordinary port-forward, port-trigger, and DMZ
machinery, but no rule that redirects the router's WAN TCP/56688 to the local
UPnP listener. The earlier external-interface test also showed that even a
packet addressed to `192.168.1.1` and routed in through the WAN interface was
dropped by the firmware-equivalent INPUT rule. Normal forwarding and DMZ
rules target downstream clients and do not bypass local INPUT filtering.

Searches of the cloud and management agents did not establish a tunnel,
reverse proxy, or localhost forward into TCP/56688. Several unrelated
components contain SSDP or UPnP client strings, but no agent was shown to
relay an external byte stream into `/Public_UPNP_C3`.

Boot-order and decompiler evidence shows:

- `/etc/rc3.d/S85wanconf` precedes `S95acos_init.sh`;
- `S95acos_init.sh` starts `acos_service`;
- the WAN-configuration path calls the NAT hook, which executes
  `arno_nat_cli_new_design stop` followed by
  `arno_nat_cli_new_design start`;
- later service paths launch `upnpd` and `soapd`;
- the compiled firewall first uses DROP policies while constructing rules and
  ultimately drops input on each external interface.

Because WAN configuration is asynchronous, static ordering alone cannot
exclude every millisecond-scale boot race. The no-firewall experiment already
bounds the consequence: wildcard UDP/1900 can answer WAN unicast before
filtering, but TCP/56688 remains bound only to the LAN address even with no
firewall. A pre-firewall interval therefore does not expose the tested TCP
connection-starvation primitive under the emulated configuration.

These mode tests use the firmware's representative NVRAM flags rather than a
complete hardware-mediated GUI transition. Physical testing remains necessary
for definitive port-role changes and boot timing.

## HTTP recovery surface

`httpd` exposes the familiar NETGEAR recovery routes and strings:

- `unauth.cgi`;
- `passwordrecovered.cgi`;
- `secure_password.cgi`;
- `MNU_access_unauthorized_checkSerial.htm`;
- `enable_password_recovery`.

It imports `system`, `popen`, `strcpy`, `strcat`, `sprintf`, and network read
functions. Focused cross-reference analysis located the recovery dispatcher in
the large function beginning at `0x46624`. That function contains the
`unauth.cgi`, `passwordrecovered.cgi`, password-recovery enable-state, serial
check, LAN-subnet, retry-state, and redirect logic.

No call to `system` or `popen` occurs in that dispatcher. Its recovery flow
uses NVRAM accessors, bounded `snprintf`/`strlcpy` calls, comparisons, template
rendering, and state-file helpers. An `sprintf` at `0x47a70` formats the
`Remote Managed Src IP=%s` diagnostic into a stack buffer beginning at
`sp+0x588`; its source is the request's previously parsed remote-address
storage, rather than a recovery answer or serial-number field. Static review
therefore did not establish a recovery-field command sink or a clear
unauthenticated overflow.

### Full-system validation status

The exact RS700 ARM `httpd` was booted with the genuine `smd`, NVRAM utility,
libraries, and web root under a full Linux/QEMU environment. The daemon
completed its initialization and reported:

```text
httpd: socket bound in 10.0.2.15:9443.
httpd: ipv6 socket bound in 80.
cert file /tmp/h.c, key file /tmp/h.k
```

The QEMU host forward could establish TCP to 9443, but the emulated daemon did
not complete its TLS handshake. This is an emulation limitation, not evidence
of a product DoS. Earlier attempts also established two hardware-integration
requirements: RS700 forces its HTTPS path even when the lab NVRAM value is
cleared, and it requires non-null certificate arguments.

Because no application request was accepted, this run cannot support a
dynamic safety conclusion about the recovery handlers. The harness and serial
evidence are retained at:

- `scripts/emulate_rs700_http_full_system.py`
- `known_firmware/emulation/RS700/full_system_http_init`
- `known_firmware/emulation/RS700/full-system-http-lab/serial.log`

Hardware or a more faithful network/TLS integration layer is still required
to exercise the real serial number, configured recovery answers, attempt
limits, and malformed request corpus.

## Mesh SOAP helper

`soap_daemon` imports `system`, `strcpy`, `sprintf`, and `memcpy`. Its two
direct `system` calls are fixed initialization commands:

```text
mkdir /tmp/soap/xml
chmod 777 /tmp/soap/xml
```

This daemon appears to orchestrate satellite clients through NVRAM/event state.
No direct external listener or attacker-controlled command string was
established, so it is lower priority than `upnpd`.

The world-writable `/tmp/soap/xml` directory is a hardening concern. It is not
a vulnerability without a demonstrated cross-process file trust or symlink
primitive.

## Binary hardening

The primary `httpd` and `upnpd` binaries are PIE, have non-executable stacks,
full RELRO/BIND_NOW, and import stack-canary failure handling. `soap_daemon`
and `genie.cgi` have non-executable stacks, RELRO, and stack-canary handling,
but static metadata did not show full RELRO/BIND_NOW.

These controls raise exploitation cost but do not prevent command injection or
denial of service.

## Disposition

- New unauthenticated RCE: not confirmed.
- New unauthenticated DoS: confirmed against the emulated LAN UPnP service;
  physical-device and device-wide impact not yet confirmed.
- WAN exposure of the DoS: not confirmed; default interface binding and
  firewall behavior reject the tested WAN path.
- Tested dynamic target: `/usr/sbin/upnpd`.
- Rejected candidate: tested standard UPnP port-mapping fields do not carry
  shell metacharacters into the `pforward_apply_dynamic` command.
- Rejected candidate: the 36-case malformed HTTP/SOAP framing corpus did not
  crash or persistently disrupt `upnpd`.
- Remaining candidates: physical-device reproduction of UPnP connection
  starvation, authenticated private SOAP actions, malformed HTTP framing
  behind a protocol intermediary, and recovery-mode `httpd`.
- Adjacent prior art: CVE-2025-12946 speed-test command execution.
- Disclosure status: retain as an emulation-confirmed DoS candidate pending
  physical-device confirmation.
