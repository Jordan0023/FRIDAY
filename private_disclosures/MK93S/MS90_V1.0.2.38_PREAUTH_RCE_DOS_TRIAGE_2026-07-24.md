# NETGEAR MK93S/MS90 V1.0.2.38 pre-authentication RCE/DoS triage

Date: 2026-07-24

## Scope

- Product: NETGEAR MK93S / MS90
- Firmware: V1.0.2.38
- Package SHA-256:
  `29a423e80f1e19f0de85b3ef0db9b81a9b73c3ec41a26aa7111bdf7af0f30d81`
- Architecture: 32-bit ARM
- Primary surfaces: proprietary `/usr/sbin/httpd`, `lighttpd`,
  `libwifihttp.so`, `dnsmasq`, and mesh services
- Status: production IPP activation and unauthenticated service DoS confirmed

## Target selection

RAX54S V1.0.17.144 was closed as a strong negative result for the tested
unauthenticated RCE/DoS surfaces. RAX54Sv2 was rejected as the immediate
follow-on because its vulnerable `ippd` binary is disabled by the same shipping
supervisor metadata already validated on RAX42v2.

MK93S was selected as the next distinct target because its current corpus
contains 42 correlated flows, including CGI input and command-execution
primitives in the web stack, and it has no completed model-specific triage in
this repository.

## Initial static result

The two `popen()`-bearing functions in the exact `libwifihttp.so` were
decompiled.

### `FUN_0001eb44`

This automated lead is rejected as request-to-command injection. The argument
passed to `popen()` is a fixed firmware string. NVRAM-derived data is used
afterward to construct or open readable diagnostic file paths; it is not
inserted into the command.

### `FUN_0002f230`

This was the strongest web lead. The function:

- reads multiple values through `get_cgi()`;
- performs extensive NVRAM reads and writes;
- reaches `_eval()` in at least one action branch; and
- contains additional unsafe-copy operations in a large request dispatcher.

Caller recovery identifies the surrounding Broadcom wireless configuration
machinery, including exported `copy_wl_index_to_unindex`. The main HTTP
dispatcher does not place `apply.cgi` in its pre-authentication exception set.
Requests outside that exception flow reach the HTTP 401 response at
`FUN_00051ea4(0x191, ...)`. This rejects `FUN_0002f230` as an unauthenticated
RCE candidate; its internal `_eval()` path remains relevant only to an
authenticated web audit.

## Authentication surface

The exact `httpd` pre-authentication test at `FUN_0004b124` was resolved rather
than inferred from strings. Its explicit exceptions are:

- `unauth.cgi`
- `securityquestions.cgi`
- `passwordrecovered.cgi`
- `multi_login.cgi`
- `WEB_site_block.htm`
- `dlna.htm`

The route dispatcher at `FUN_00052228` separately names its permitted CGI
handlers and emits HTTP 404 for unknown routes. `apply.cgi` is absent from the
pre-authentication exceptions.

The handler table maps `unauth.cgi` to `FUN_00070358` and
`passwordrecovered.cgi` to `FUN_00070664`. The first only checks
`enable_password_recovery` and selects a fixed redirect. The second reads two
request fields into 2048-byte buffers through a size-aware helper, transforms
them into 128-byte bounded values, compares them with stored recovery answers,
and writes only fixed/formatted state. No command sink or unbounded
request-to-stack copy was found in either handler.

The SOAPAction parser at `FUN_000770a8` was also caller-checked. It caps the
header extraction at 255 bytes and copies the parsed service/action components
into two 256-byte caller buffers in `FUN_00077500`; therefore its apparent
`strcpy()` calls are bounded by the preceding extraction. The caller dispatches
only exact service/action pairs from a static table. Individual table handlers,
especially entries whose flags permit execution without the SOAP login token,
remain the strongest unclosed web surface.

### Static SOAP SessionID bypass candidate

Reconstruction of the table at `0x0018003c` produced exact
service/action/handler/flag tuples. In `FUN_00077500`, normal table entries with
flags such as `0x7c` are dispatched when the supplied `SessionID` either
matches `soap_Auth_SessionID` **or equals the firmware literal
`12345678901234567890`**. This comparison is outside `SOAPLogin` and applies to
configuration-changing actions.

High-impact examples carrying flag `0x7c` include:

- `DeviceConfig#CreateAdmin` -> `FUN_0009b2dc`
- `DeviceConfig#UpdateAdminPassword` -> `FUN_0009b3cc`
- `DeviceConfig#UpdateAdminPasswordHashed` -> `FUN_0009b4dc`
- `DeviceConfig#Reboot` -> `FUN_0009ca48`
- `DeviceConfig#ResetToFactoryDefault` -> `FUN_0009d4d4`

The credential handlers reach their account/password update routines after
bounded XML extraction. `Reboot` sets the daemon's global reboot flag.
`ResetToFactoryDefault` calls a fixed system command and sets two reset/reboot
flags. Consequently, if the literal SessionID is accepted in a production
request, it is at minimum an authentication bypass enabling remote
administrative credential replacement and intentional service/device DoS.

An exact full-system ARM lab was built and the genuine MS90 `httpd` remained
stable on TCP/443. Resolving `FUN_0004b3c0` showed that the apparent
model-specific `isToRouter` failure was a Host check: in this lab state the Host
must equal the configured `lan_ipaddr` (`10.0.2.15`).

With that correction, the following no-credential controls reached the genuine
SOAP dispatcher:

- missing SessionID: SOAP `ResponseCode 401`;
- `FRIDAY_INVALID_SESSION`: SOAP `ResponseCode 401`;
- `12345678901234567890`: `DeviceInfo#GetInfo` dispatched as function index 7
  and returned `ResponseCode 000`, model `MS90`, firmware `V1.0.2.38`.

The fixed-token `DeviceConfig#Reboot` request then dispatched function index 79,
returned `RebootResponse` with `ResponseCode 000`, and produced
`sa_rebootRequired` in the genuine daemon log. This dynamically confirms the
authentication bypass and unauthenticated invocation of the production reboot
path. The generic QEMU platform cannot complete the board-specific Ethernet
power-down/reboot sequence, so complete guest disappearance was not reproduced;
that is an emulator limitation after the reboot decision, not an authentication
or handler-reachability limitation.

## Next validation

1. Decompile the `securityquestions.cgi` table behavior and any shared parsing
   helper not already covered by `FUN_00070664`.
2. Audit the proprietary SOAP pre-authentication dispatcher independently; it
   is not routed through the wireless `apply.cgi` exception logic. The parser
   itself is rejected, its table is resolved, and the fixed SessionID bypass
   plus reboot-handler reachability are dynamically confirmed.
3. If a concrete parameter-to-memory or parameter-to-command flow emerges,
   boot the exact daemon in a network-isolated ARM lab and run
   control/invalid-session/no-credential cases.
4. Treat a crash as a DoS only if a specific input reproducibly removes the
   service and a same-sized benign control does not.

## Disposition

- Confirmed unauthenticated RCE: **no**
- Confirmed unauthenticated service DoS: **yes, when IPP printer
  configuration is enabled**
- Fixed-command `popen()` false positive rejected: **yes**
- CGI-to-`_eval()` candidate reachable without authentication: **no**
- Password-recovery handler RCE/DoS found in this pass: **no**
- SOAP fixed-SessionID authentication bypass: **dynamically confirmed**
- Unauthenticated SOAP reboot/DoS path invocation: **dynamically confirmed;
  final board reset inferred because generic QEMU lacks the hardware power/reset
  path**

## IPP reachability correction

The exact shipping `libcms_core.so` contains `rcl_ippCfgObject`, which writes
`/var/printers.ini` and sends `CMS_MSG_START_APP` for EID 45 with that pathname
in the optional message body. A corrected full-system experiment using the
genuine MS90 `/bin/smd`, active entity metadata, libraries, and exact `ippd`
confirmed:

```text
startApp: setting optional args /var/printers.ini
launchApp: spawning //bin/ippd args  /var/printers.ini
parseArgs: argv[1] = /var/printers.ini
IPPD_ALIVE=yes
IPPD_LISTENING=yes
00000000:0277 ... 0A
```

The daemon hash is byte-identical to the RAX29/RAX30-family binary for which
the unauthenticated 257-byte URI reproducibly terminates the listener. The
earlier no-listener result omitted the CMS message body and did not reproduce
the complete production callback.
