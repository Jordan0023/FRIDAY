# GL.iNet Brume 2 4.7.4 Unauthenticated Global Login DoS

## Vulnerability status

**Technical status:** Confirmed  
**Novelty status:** Zero-day candidate; public novelty not conclusively established  
**Authentication required:** No  
**Impact:** Administrative WebUI authentication denial of service  
**Affected product tested:** GL.iNet GL-MT2500/GL-MT2500A Brume 2  
**Affected firmware tested:** 4.7.4  
**RCE status:** No unauthenticated RCE demonstrated  

## Executive summary

GL.iNet Brume 2 firmware 4.7.4 contains an unauthenticated,
process-global login-failure counter in the `gl-ngx-session` service. An
unauthenticated network client that can reach the router's administrative
WebUI can submit ten invalid JSON-RPC challenge requests. The tenth failure
sets a global 600-second authentication lockout.

The lockout is not associated with the attacking source address, username, or
session. A second, independently addressed client is consequently prevented
from obtaining a legitimate root challenge and from submitting a correctly
computed root login response.

The behavior was reproduced through the firmware's native AArch64 Nginx/
OpenResty, Lua RPC handler, Ubus daemon, Eco runtime, and
`gl-ngx-session` service in an isolated two-client emulation environment.

Ordinary HTTP and the tested native services remained responsive. The finding
is therefore an administrative authentication-plane denial of service, not a
demonstrated whole-router or forwarding-plane outage.

## Proposed title

## Root cause

The session service maintains login protection in process-global Lua
variables:

```lua
local login_wait = 0
local login_fail = 0
```

The configured defaults are ten failures and a 600-second wait:

```lua
login_fail_max_cnt =
    tonumber(c:get("oui-httpd", "main", "max_login_fail") or 10)
login_fail_wait_time =
    tonumber(c:get("oui-httpd", "main", "login_fail_wait") or 600)
```

Invalid authentication activity increments the shared failure counter. Once
the maximum is reached, the code assigns the wait deadline to the shared
`login_wait` variable:

```lua
login_fail = login_fail + 1
login_wait = sys.uptime() + login_fail_wait_time
```

Subsequent authentication operations check the same process-global deadline:

```lua
if login_wait - sys.uptime() > 0 then
```

Because this state is not scoped to a source address, account, browser, or
session, failures generated by one unauthenticated client deny authentication
to unrelated legitimate clients.

## Attack requirements

An attacker requires:

1. Network access to the router's administrative HTTP or HTTPS service.
2. The ability to send JSON-RPC requests to `/rpc`.

The attacker does not require:

- a valid username/password combination;
- an authenticated session;
- an administrator token;
- local shell access; or
- physical access.

Actual exposure depends on deployment. The impact is normally limited to
clients able to reach the management interface. Internet exploitability
requires the administrative interface to be exposed or forwarded to an
untrusted network.

## Reproduction

The triggering request is an unauthenticated JSON-RPC challenge for a
nonexistent account:

```http
POST /rpc HTTP/1.1
Host: ROUTER
Content-Type: application/json

{"method":"challenge","params":{"username":"attacker"}}
```

The request returns:

```json
{
  "id": null,
  "jsonrpc": "2.0",
  "error": {
    "message": "Access denied",
    "code": -32000
  }
}
```

Submit the request ten times from client A. A legitimate root challenge from
client B then returns:

```json
{
  "id": null,
  "jsonrpc": "2.0",
  "error": {
    "message": "Login fail number over limit",
    "data": {
      "wait": 600
    },
    "code": -32003
  }
}
```

A correctly computed response for a root challenge obtained before the
trigger was also rejected:

```json
{
  "id": null,
  "jsonrpc": "2.0",
  "error": {
    "message": "Login fail number over limit",
    "data": {
      "wait": 580
    },
    "code": -32003
  }
}
```

## Dynamic confirmation

The test used an internal-only container network without published host
ports:

| Role | Address |
|---|---|
| Emulated router | `172.24.0.2` |
| Attacking client A | `172.24.0.3` |
| Legitimate client B | `172.24.0.4` |

The emulated router ran:

- firmware `/sbin/ubusd`;
- firmware `/usr/bin/eco`;
- firmware `/usr/sbin/gl-ngx-session`;
- firmware `/usr/sbin/nginx`;
- firmware OpenResty modules and Lua `/rpc` handler;
- firmware dynamic loader and libraries.

QEMU user-mode supplied only AArch64 CPU translation.

Observed sequence:

1. Client B obtained a valid root challenge.
2. Client A submitted ten invalid unauthenticated challenges.
3. All ten requests returned error `-32000`.
4. Client B's next legitimate root challenge returned `-32003` with a
   600-second wait.
5. Client B's correctly computed root response returned `-32003` with
   580 seconds remaining.
6. Ordinary HTTP still returned status 200 in 0.041311 seconds.
7. The firmware Ubus socket, session daemon, and Nginx master remained alive.

This proves that one unauthenticated client can deny WebUI authentication to a
different client without crashing the Web server or session service.

## Security impact

An attacker on a network that can reach the management interface can prevent
administrators from authenticating for approximately ten minutes. The attack
can be repeated after the wait period, allowing continued denial of
administrative access with very little traffic.

Potential operational consequences include:

- delayed incident response;
- inability to change firewall, VPN, DNS, or routing settings through the
  WebUI;
- inability to revoke users or alter credentials through the WebUI;
- disruption of routine administration; and
- pressure to physically reboot or reset the device.

Existing authenticated sessions and non-WebUI management mechanisms were not
evaluated. Network forwarding was not shown to fail.

## Severity assessment

Suggested CVSS v3.1 vector:


Suggested base score: **4.3**

## CWE classification

Potential classifications:

- **CWE-307:** Improper Restriction of Excessive Authentication Attempts
- **CWE-400:** Uncontrolled Resource Consumption

CWE-307 most directly describes the flawed lockout design: protection against
authentication guessing is implemented in a way that allows an
unauthenticated party to lock out unrelated users.

## Zero-day classification

This report documents a confirmed vulnerability in the tested firmware.
However, a vulnerability is only conclusively established as a zero-day when
prior public disclosure, vendor knowledge, and fix availability have been
adequately checked.

The defensible wording is:

> Confirmed, previously undocumented in this research, unauthenticated WebUI
> authentication denial of service and zero-day candidate affecting GL.iNet
> Brume 2 firmware 4.7.4.

Vendor confirmation is not required to prove the technical behavior.
Vendor coordination or a comprehensive prior-art review is required to make a
strong novelty claim.

## Scope limitations

This research confirms:

- an unauthenticated trigger;
- cross-client impact;
- a process-global authentication lockout;
- approximately 600 seconds of denied authentication;
- continued availability of ordinary HTTP; and
- survival of the tested native services.

It does not confirm:

- loss of packet forwarding;
- loss of Internet connectivity;
- denial of SSH or other management channels;
- persistence across service or device restart;
- unauthenticated command execution;
- unauthenticated RCE;
- exploitation from the public Internet under default configuration;
- every Brume 2 firmware release; or
- public novelty.

## Recommended remediation

GL.iNet should replace the process-global counter with controls that cannot be
used to deny service to unrelated clients:

1. Scope counters to both account and source address.
2. Apply short, progressive delays instead of a global ten-minute lockout.
3. Do not increment an account-wide counter for nonexistent usernames.
4. Maintain a safe recovery path for legitimate local administrators.
5. Bound and expire per-source tracking state to prevent memory exhaustion.
6. Log and rate-limit repeated failures without disabling all authentication.
7. Add regression tests using two independently addressed clients.

An effective regression test must prove that failures from client A do not
prevent a valid challenge and login from client B.

## Workarounds

Until fixed:

- restrict WebUI access to trusted management hosts;
- place management access on a dedicated trusted VLAN;
- disable management access from WAN and guest networks;
- use firewall rules to limit access to ports 80 and 443;
- monitor repeated `/rpc` authentication failures; and
- retain a separately protected recovery-management method.

Rebooting or restarting the session service may clear the in-memory state, but
it does not remediate the vulnerability and should not be treated as a
security fix.

## WAN reachability follow-up

Firmware analysis confirms a supported conditional WAN path. Nginx exposes
`/rpc` through wildcard IPv4 and IPv6 listeners on TCP/443. The stock WAN zone
rejects router-local input, but GL.iNet's shipped DDNS remote-HTTPS
configuration creates an `https_wan` rule accepting WAN TCP/443. The rule
opens the same Nginx server and `/rpc` handler.

Accordingly, this is a **configuration-dependent unauthenticated remote
administrative DoS when GL.iNet DDNS remote HTTPS is enabled**, while remaining
blocked from the stock WAN zone when that feature is disabled. Physical
WAN-side confirmation remains pending.

## Conclusion

GL.iNet Brume 2 firmware 4.7.4 has a confirmed unauthenticated
administrative WebUI authentication denial of service. Ten invalid challenge
requests from one unauthenticated client impose a process-global lockout that
blocks a separate legitimate client for approximately 600 seconds.

The vulnerability is technically confirmed and suitable for coordinated
disclosure. It should be described as a zero-day candidate unless and until
novelty is independently established.
