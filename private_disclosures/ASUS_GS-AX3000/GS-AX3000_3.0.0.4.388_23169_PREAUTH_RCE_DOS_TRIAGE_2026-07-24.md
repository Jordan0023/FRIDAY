# ASUS ROG STRIX GS-AX3000 3.0.0.4.388_23169 pre-auth RCE/DoS triage

Date: 2026-07-24

## Result

No unauthenticated RCE or reliable input-specific denial of service was
confirmed in this pass.

One concrete authentication-boundary defect was confirmed in genuine component
emulation: several nominally protected handlers continue executing after
`httpd` emits its unauthenticated login redirect. In particular,
`netool.cgi` reached the genuine `rc` net-tool worker and returned its
`"successful"` result without credentials. This is a real pre-authentication
execution primitive, but the bounded command-injection and availability tests
below did not turn it into RCE or DoS.

This is a negative triage result, not a statement that the firmware is free of
vulnerabilities. The important improvement over the earlier automated report
is that this pass extracted and examined the real root filesystem. The earlier
report only saw the outer UBI/update container and therefore missed the actual
network daemons and route table.

The RAX30 GENA-callback crash and EX2800 unconfigured `webupg` command
injection do not transfer directly:

- GS-AX3000 uses ASUSWRT `miniupnpd`, not the vulnerable NETGEAR/Broadcom
  RAX30 daemon.
- It has no EX2800 `mini_httpd`, `webupg`, `/start_telnet`, or corresponding
  unconfigured authentication-bypass chain.
- ASUS-specific follow-up identified `netool.cgi`, setup/QIS routes, and
  command-building code, but this pass did not prove an unauthenticated
  attacker-controlled value reaching a command-execution sink.

Do not describe this firmware as affected by a new zero-day based on the
present evidence.

## Corrected extraction

The inner `.w` file is a UBI image with four volumes. Its volume named
`rootfs_ubifs` is actually a little-endian SquashFS 4.0 filesystem compressed
with XZ. Direct `ubireader_extract_files` therefore fails with:

```text
UBIFS Fatal: Super block error: Wrong node type.
```

The successful sequence was:

```text
ubireader_extract_images -o /tmp/friday-gsax3000-ubi-images INNER.w
unsquashfs -d known_firmware/extracted/e00687bef11f4a67/gs-ax3000-rootfs \
  /tmp/friday-gsax3000-ubi-images/.../img-739723882_vol-rootfs_ubifs.ubifs
```

The recovered filesystem contains 2,585 files, 221 directories, and 708
symlinks.

## Targeted HTTP decompilation

Ghidra analyzed the genuine `httpd` as ARM little-endian and recovered the
main request dispatcher at `0x0001b114`.

The dispatcher:

- parses the request line and headers into bounded global buffers;
- truncates the normalized route to 127/128 bytes;
- looks up the route in separate handler and authentication tables;
- applies setup/authentication state checks before dispatch;
- invokes `check_noauth_referrer` through `FUN_00083404` for applicable
  no-auth routes; and
- invokes the selected handler only after the route/authentication decision.

`FUN_00083404` returns an error when a required no-auth referrer is absent or
does not match the stored value. This makes a route name alone insufficient
to classify a handler as unauthenticated.

The `QIS_default.cgi` handler is present and constructs a redirect using a
128-byte stack buffer and bounded `snprintf`. The common redirect helper
applies the XSS blacklist, copies into a 128-byte destination using `strlcpy`,
and rejects angle brackets before reflection. No overflow or command sink was
identified in this route-local flow.

The binary also exposes a `SystemCmd` path and shell-command template, but the
current analysis did not recover a pre-auth route-to-`SystemCmd` flow. It must
remain a lead, not an RCE candidate.

## RAX30-method transfer

The genuine `miniupnpd` implements GENA `SUBSCRIBE`/`UNSUBSCRIBE` and includes
the normal callback parser and event-notification paths. It is not byte
identical to the RAX30 daemon and uses the MiniUPnPd-style messages:

```text
Invalid Callback in SUBSCRIBE %.*s
ProcessHTTPSubscribe %s
addSubscriber(%s, %.*s, %d)
```

Static presence of the GENA surface is not evidence that the RAX30 callback
crash transfers. A genuine-daemon runtime matrix is still needed for short,
boundary, oversized, malformed-bracket, duplicate-header, `TIMEOUT`, `NT`,
and SID cases. No crash is claimed here.

## EX2800-method transfer

No matching EX2800 components or chain were found:

- no `mini_httpd`;
- no `webupg`;
- no `/start_telnet`;
- no EX2800 query-string loader; and
- no matching one-shot unconfigured upgrade bypass.

ASUSWRT does have an unconfigured/setup state controlled by NVRAM and QIS
routes. That is a product-specific attack surface, but it is not the EX2800
primitive and requires its own stateful authentication matrix.

## Dynamic attempt

The repository's network-isolated Greenhouse workflow was invoked against the
local archive with Docker networking disabled. Greenhouse's generic unpacker
stopped at the same mislabeled UBI/SquashFS boundary:

```text
Unable to find a proper root directory for
/tmp/scratch/input/_firmware.zip.extracted
Error, unable to unpack image for /input/firmware.zip
```

The run was stopped after this terminal extraction error rather than allowed
to consume its full time bound. No network target or physical device was
contacted.

## Genuine ARM component validation

A follow-up ran the manually extracted ARM components under
`qemu-arm-static` in a disposable Docker container with `--network none`. The
lab used the genuine `httpd`, `miniupnpd`, `libwebapi.so`, `rc`, firmware
libraries, a minimal NVRAM compatibility shim with `x_Setting=0`, and a
firewall-bookkeeping-only MiniUPnPd shim.

The HTTP control returned the genuine factory-setup redirect to
`/QIS_wizard.htm?flag=welcome`.

### Confirmed authentication continuation

Unauthenticated requests to `cfg_onboarding.cgi`, `check_Auth.cgi`,
`netool.cgi`, `upload_server_ovpn_cert.cgi`, and `caupload.cgi` produced two
HTTP status lines on one connection. This proves execution continued after the
authentication redirect.

`check_Auth.cgi` emitted its `{"asus_auth":"OK"}` object after the redirect.
With the genuine `rc` process launched as its `netool` applet,
`netool.cgi` returned its `"successful"` object for attacker-controlled
diagnostic requests. NVRAM-write instrumentation independently recorded entry
into each named handler.

In contrast, `apply.cgi`, `applyapp.cgi`, `appGet.cgi`, and generic
`upload.cgi` returned only the login response. A `SystemCmd` marker submitted
to `apply.cgi` was not executed.

### Net-tool RCE and DoS tests

The pre-authentication net-tool path accepted normal targets and the
space/dash option shape. Semicolon, `$()`, backtick, and `%n` canaries created
no marker files. No RCE was confirmed.

A bounded burst of 40 simultaneous unauthenticated requests used:

```text
/netool.cgi?type=3&target=192.0.2.1&pcnt=1&response=10&exec=10
```

All HTTP requests completed. Independent `Main_Login.asp` controls before,
during, and after the burst remained live; the longest coarse component-lab
latency was one second. No daemon death or persistent management outage was
observed.

The user-mode lab cannot transparently execute ARM child programs created by
the worker's `/bin/sh`. This rejects an immediate HTTP/net-tool crash but does
not fully close physical-device resource exhaustion.

### HTTP parser and setup-route tests

The genuine daemon remained live after header values and paths through 65,536
bytes, conflicting or invalid content lengths, chunked-plus-length requests,
QIS/page redirect values through 4,096 bytes, and script, quote, CRLF, and
scheme-relative redirect canaries. Large requests were truncated, rejected, or
closed without terminating the service.

The NVRAM trace showed only route and QIS bookkeeping for these cases. The
submitted protected configuration and `SystemCmd` values were not applied.

### UPnP result

The genuine MiniUPnPd 2.2.0 parser remained live after every RAX30-derived
case: malformed callback brackets, the RAX30-shaped callback, duplicate
headers, malformed timeout, `NT` through 4,096 bytes, callbacks through 16,384
bytes, and SOAPAction values through 16,384 bytes. Invalid callbacks returned
HTTP 412 and malformed SOAP actions returned HTTP 500. Every case was followed
by a successful descriptor control. The RAX30 GENA DoS is tested negative.

### Upload-handler result

Unauthenticated dispatch reaches the OpenVPN upload output handler and toggles
its temporary NVRAM state, but the multipart POST did not populate the archive
with attacker bytes in this lab. The handler created an empty staging file,
then attempted to remove the staging directory. It did not execute the marker
archive or write outside the staging directory.

Decompiler review of `libwebapi.so` recovered this later extraction command:

```text
tar -xzf /tmp/server_ovpn_file/server_ovpn.tgz -C /tmp/server_ovpn_file
```

The shipped BusyBox `tar`, tested independently, follows a symlink pivot and
can write a marker outside the extraction directory. That is a dangerous
extractor primitive. However, the tested unauthenticated request did not place
attacker-controlled bytes into `server_ovpn.tgz`, so the required pre-auth
chain is not established. It remains a physical/full-system validation lead,
not a confirmed arbitrary-write or RCE finding.

### OpenVPN upload follow-through

The upload lead was followed through with the route's exact genuine handler
pair recovered from the `httpd` MIME table:

- `FUN_000277e8` is the multipart input handler. It searches for
  `name="import_cert_file"`, writes
  `/tmp/server_ovpn_file/server_ovpn.tgz`, rejects bodies above `0x19000`
  bytes, and stops at the multipart CRLF boundary.
- `FUN_0002b0f0` calls `upload_server_ovpn_cert_cgi()`, which checks both the
  temporary NVRAM result and staging-file existence before running `tar`.

The isolated lab was corrected so the NVRAM shim retained
`upload_server_ovpn_cert_temp` rather than merely logging it. A command-capture
shim suppressed cleanup so the staging directory could be inspected. Three
sub-limit requests were replayed: the exact form boundary, a quoted boundary,
and a browser-shaped WebKit boundary with the genuine `import_cert_file`
field.

All three requests reached the route, but each set
`upload_server_ovpn_cert_temp=0`, created no staging archive, and invoked only
the cleanup command:

```text
rm -rf /tmp/server_ovpn_file
```

No `tar -xzf` command was reached. Because cleanup was intercepted, absence of
the archive is not attributable to post-request deletion. The result is
consistent with authentication continuation into the response/output path
while the unauthenticated multipart input is not accepted. The independently
confirmed BusyBox symlink behavior therefore remains unreachable through this
pre-auth request path. This follow-through tests the OpenVPN lead negative for
unauthenticated arbitrary write and RCE.

## Unconditional-WAN assessment

**Result: no unconditional WAN-reachable unauthenticated RCE or DoS was
established.** The current leads fail at two independent prerequisites:
factory WAN exposure and configured-state unauthenticated dispatch.

The exact compiled defaults recovered from `usr/lib/libshared.so` include:

- `fw_enable_x=1`;
- `misc_http_x=0` (WAN web administration disabled);
- `wan_upnp_enable=0` and `upnp_enable=0`;
- `autofw_enable_x=0`, `vts_enable_x=0`, and an empty DMZ address;
- `enable_webdav=0`, `ftp_wanac=0`, `pptpd_enable=0`;
- `telnetd_enable=0` and `sshd_enable=0`; and
- `ipv6_service=disabled` with `ipv6_fw_enable=1`.

The firewall implementation in the genuine `rc` image constructs separate
WAN/LAN chains and a default-drop INPUT policy. Thus the LAN HTTP behavior
seen during factory setup is not, by itself, WAN reachable under the compiled
factory policy.

The genuine `httpd` was then rerun with `x_Setting=1`, representing a normally
configured router. Every tested unauthenticated route—including
`cfg_onboarding.cgi`, `check_Auth.cgi`, `netool.cgi`,
`upload_server_ovpn_cert.cgi`, and `caupload.cgi`—stopped after the login
redirect. There was no second response, handler success, net-tool execution,
or configuration mutation. The authentication-continuation behavior is
therefore conditional on `x_Setting=0`.

The port-mapping alternative was also tested against genuine MiniUPnPd in
secure mode. An `AddPortMapping` request targeting the router itself returned
HTTP 500 / UPnP error 718 and the daemon remained live. PCP/NAT-PMP cannot
provide an unconditional factory path when the shared mapping service is
disabled by `upnp_enable=0`; enabling such a service would itself be a
configuration prerequisite.

Consequently, increasing net-tool concurrency or running the upload workload
cannot establish *unconditional WAN* impact: after setup those handlers are
authentication-gated, while at factory defaults WAN web administration and
the mapping service are disabled. The remaining hypotheses are conditional:

1. factory-unconfigured, LAN-local access to the QIS/net-tool paths; or
2. an administrator first enabling WAN administration, UPnP, port forwarding,
   DMZ, or changing the firewall policy.

Neither satisfies an unconditional WAN finding. A physical-device test can
validate implementation fidelity, but it would need to demonstrate an
independent default-WAN reachability bypass before any of these application
leads could qualify.

## Public-prior-art boundary

The search on 2026-07-24 found substantial prior GS-AX3000 security history.
In particular, public 2023 coverage lists GS-AX3000 among models affected by
ASUS router issues including CVE-2022-35401 and CVE-2023-28703. Those are
prior art and must not be relabeled as new findings.

The vendor's immediately preceding `3.0.0.4.388_23166` release notes say it
hardened AiCloud credential/path/command handling, web-history command
filtering, VPN upload validation, legacy string handling, and a user-setting
bypass. Version `_23169` postdates those fixes. Any apparent match in those
areas must first be tested against the documented fixes and known CVEs.

## Next validation work

The component lab has now covered both setup states and the primary network
services. If stronger assurance is required, the next step is physical-device
confirmation with the WAN interface attached only to an isolated test host.
It should:

1. record a factory-default WAN port scan for TCP and UDP;
2. confirm WAN HTTP/HTTPS and UPnP/PCP/NAT-PMP are unreachable;
3. complete setup, repeat the scan, and replay the configured-state HTTP
   matrix;
4. enable each exposure feature individually to distinguish conditional
   behavior from defaults; and
5. treat a DoS as confirmed only when one input deterministically causes a
   fault or persistent service loss with a healthy control.

Physical-device confirmation is required before product impact is asserted.
