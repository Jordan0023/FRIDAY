# R7350 V1.2.0.92 unauthenticated UPnP DoS triage

## Status

Strong candidate, dynamically reproduced against the genuine firmware binary in
an isolated localhost-only emulator. This is not yet labeled a zero-day or a
vendor-ready confirmed vulnerability because physical-device reproduction and
vendor-coordinated novelty checking remain outstanding.

## Target identity

- Product: NETGEAR R7350
- Firmware: V1.2.0.92
- Package SHA-256:
  `88cd8895b9ec363660d571e179664077e09f8233ed69af05e0bb0fa48727adf4`
- `usr/sbin/miniupnpd` SHA-256:
  `d45b00e9b2c9a4411df17b0134a672bc88ee0ea90a140ee34a8d29e3ab199678`
- Architecture: MIPS32 little-endian, uClibc

## Root cause

`Process_upnphttp` receives at most 0x800 bytes per iteration, then performs:

1. `realloc(req_buf, received + req_buflen + 1)`
2. `memcpy(req_buf + req_buflen, incoming, received)`
3. a linear scan for `\r\n\r\n`
4. return to the event loop if no terminator exists

There is no maximum request-header size. Reallocation and rescanning occur for
every 2 KiB increment. A client can therefore keep one unauthenticated TCP
connection open and force unbounded allocation plus approximately quadratic
copy/scan work.

Focused pseudocode is retained in:

- `router-agent-results/20260724T-r7350-upnp-audit/targets.c`
- function `Process_upnphttp` at Ghidra address `0001684c`

## Dynamic result

The genuine daemon was run under `qemu-mipsel-static` in a disposable Docker
network. Only the emulation-specific failure to configure an SSDP multicast
notify socket was bypassed at runtime with GDB; the HTTP parser and binary were
unmodified. Docker published the HTTP listener only on `127.0.0.1`.

Clean idle baseline:

- VmRSS: 7,228 KiB
- VmData: 149,212 KiB
- guest process CPU ticks: user 3, system 1

During one 64 MiB unterminated-header attempt:

- VmRSS: 29,600 KiB
- VmData: 171,496 KiB
- host QEMU process: 75.8% CPU after 77 seconds
- guest process CPU ticks: user 7,622, system 34
- sender remained blocked and had not completed after 77 seconds

After terminating the sender:

- VmRSS: 31,264 KiB
- VmData: 173,160 KiB
- guest user CPU ticks had reached 10,304

Five concurrent control requests still received 404 responses, but latency was
48–90 ms under pressure. The principal impact is sustained CPU exhaustion and
attacker-controlled memory growth; the effect on the physical router's limited
RAM/CPU must still be measured.

The localhost-restricted reproducer is:

- `router-agent-results/20260724T-r7350-upnp-audit/r7350_upnp_header_pressure.py`

## Authentication and exposure

The vulnerable parser runs before any SOAP action and before any authentication.
UPnP is normally LAN-scoped, so the expected vector is an unauthenticated
adjacent-network client when UPnP is enabled.

## Controls and exclusions

- A normal unknown-path GET returned HTTP 404 and left the daemon running.
- A request for `rootDesc.xml` crashed in the incomplete extracted environment;
  that result is excluded because `/etc` was sanitized during extraction and
  descriptor-generation state was unavailable.
- The diagnostic CGI `c4_IPAddr` command template was reviewed separately. It
  rejects `-` and `;` and invokes an additional validator, so it is not reported
  as unauthenticated command injection.
- `brs_ping` uses fixed commands and is not reported as command injection.

## Novelty check

Searches found CVE-2026-5720, a different miniupnpd SOAPAction integer-underflow
issue, and NETGEAR PSV-2021-0273, fixed for R7350 before V1.2.0.90. No public
record found in this pass specifically describes the unterminated-header
reallocation/rescan condition on V1.2.0.92. Absence from search results is not
proof of novelty.

## Required confirmation

1. Repeat with an owned R7350 V1.2.0.92 on an isolated LAN.
2. Record UPnP PID, RSS, CPU, request progress, service latency, and recovery.
3. Repeat at increasing sizes and multiple simultaneous connections.
4. Confirm whether the daemon is killed, restarted, or causes router-wide
   watchdog reboot.
5. Run a final CVE/vendor-advisory and binary-lineage novelty comparison before
   coordinated disclosure.

## Suggested remediation

Enforce a small hard cap on request headers before `realloc` (for example,
16–32 KiB), reject oversized/incomplete headers with 431/400, avoid repeated
whole-buffer growth, and apply per-client read deadlines.
