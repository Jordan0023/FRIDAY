# OpenWrt AFOUNDRY EW1200 25.12.5 pre-authentication RCE/DoS triage

Date: 2026-07-24  
Status: first-pass static and bounded dynamic review complete; no
unauthenticated RCE or persistent DoS confirmed

## Result

No unauthenticated remote-code-execution or denial-of-service vulnerability
was confirmed in the AFOUNDRY EW1200 OpenWrt 25.12.5 image during this pass.

This is a negative research result, not a claim that the firmware is
vulnerability-free. The genuine `uhttpd` HTTP parser was tested under MIPS
user-mode emulation, but LuCI, rpcd, ubus, wireless, DHCP and DNS services were
not reproduced together as a complete running router.

## Authentication and exposure boundary

The default configuration binds HTTP and HTTPS to all IPv4 and IPv6
addresses. The stock firewall accepts input from the LAN zone and rejects
input from the WAN zone. Accordingly, the management surface is
unauthenticated-LAN reachable but not stock-WAN reachable.

The only explicitly unauthenticated rpcd permissions found were:

- `session.access`
- `session.login`
- `luci.getFeatures`

The unauthenticated ACL does not grant `cgi-io`, file-write, command execution,
configuration-write, or arbitrary ubus permissions.

The firmware image has an initially empty root password:

```text
root:::0:99999:7:::
```

This is normal OpenWrt first-boot behavior and must be treated as a deployment
state, not mislabeled as an authentication bypass. A physical/default-state
test should nevertheless measure exactly which services permit an empty
password before initial setup and whether the setup network is isolated.

## Focused `cgi-io` review

Ghidra evidence initially correlated attacker-facing reads with `execl`,
`strcpy`, file opens and copies in four functions:

- `FUN_00401730` at `0x00401730`
- `FUN_00401a50` at `0x00401a50`
- `FUN_00401b50` at `0x00401b50`
- `FUN_00401dfc` at `0x00401dfc`

Focused pseudocode did not establish a pre-authentication exploit:

- `FUN_00401730` invokes `/bin/busybox` with fixed `md5sum` or `sha256sum`
  applet names; the file path is a separate `execl` argument, not shell text.
- The multipart parser allocates its boundary string from the measured input
  length and protects its 4 KiB stack buffer with a stack canary.
- Upload and download paths pass through `ubus_rpc_session` checks.
- Downloads require both `cgi-io.download` permission and a `file` ACL match
  on the canonicalized requested path.
- Direct unauthenticated executions of all four CGI personalities exited with
  failure when no ubus session was available.

No attacker-controlled string-to-shell flow was identified.

## Bounded genuine-uHTTPd parser validation

The genuine MIPS `uhttpd` from the firmware was launched on
`127.0.0.1:28081` under QEMU user-mode emulation. Static HTTP serving returned
200 and was used as the post-probe liveness control.

The bounded probe corpus in
`scripts/probe_openwrt_uhttpd_security.py` produced:

| Case | Response | Daemon survived |
|---|---|---|
| Negative Content-Length | 400 | yes |
| Conflicting Content-Length | 400 | yes |
| Unsupported Transfer-Encoding | 501 | yes |
| Invalid chunk length | 502 | yes |
| Oversized chunk length | 502 | yes |
| Transfer-Encoding plus Content-Length | 400 | yes |
| 8 KiB header name | 413 | yes |
| 8 KiB request target | 413 | yes |

No crash, persistent listener loss, or request-smuggling acceptance was
observed in this corpus.

LuCI returned 502 in this partial lab because the CGI shebang resolves
`/usr/bin/env ucode` in the host execution context and the router's ubus/rpcd
runtime was absent. This is a lab limitation, not evidence of a firmware
failure.

## Full ubusd/rpcd/uHTTPd authentication validation

The genuine MIPS `ubusd`, `rpcd`, all shipped rpcd plugins, and `uhttpd` were
subsequently run together from a disposable copy of the firmware filesystem.
The stack exposed only `127.0.0.1:28082`. Host entropy was bound read-only into
the private mount namespace so rpcd could create genuine random session IDs.

Observed authentication results:

- factory-empty root password: rejected;
- incorrect root password: rejected;
- correct password set with the firmware's own BusyBox `passwd`: accepted;
- forged session ID: rejected;
- missing session ID: rejected;
- one-second session after expiry: rejected.

Observed authorization results:

- unauthenticated `file.exec`: access denied;
- unauthenticated `luci.getFeatures`: allowed as declared by the ACL;
- a valid root session was denied execution of `/bin/echo`, which is absent
  from its file-exec allowlist;
- an allowlisted `/bin/dmesg -r` call passed the ACL and reached execution;
- a disposable restricted account granted only the `unauthenticated` read
  group could call `luci.getFeatures`;
- that restricted account was denied `file.exec` and reads of `/etc/shadow`.

The allowlisted command returned exit 127 because a child MIPS binary launched
by rpcd is not automatically QEMU-wrapped in this user-mode lab. The distinct
ACL result and attempted child execution still establish the authorization
boundary without treating the lab limitation as firmware behavior.

## Genuine cgi-io ACL and multipart validation

`scripts/probe_openwrt_cgi_io_security.py` invoked the genuine `cgi-upload`
personality against the live rpcd session service:

| Case | Result | Target created |
|---|---|---|
| Missing session | `Upload permission denied` | no |
| Forged session | `Upload permission denied` | no |
| Restricted valid session | `Upload permission denied` | no |
| Root valid session | accepted | yes |
| Missing closing multipart boundary | no output, clean exit | no |
| File part without a filename attribute | accepted for ACL-approved target | yes |
| 8 KiB multipart boundary | accepted | yes |

All writes were confined to `/etc/luci-uploads/` in the disposable filesystem,
which is explicitly granted by the root session's ACL. No ACL bypass, crash,
out-of-scope write or persistent hang was observed.

The checksum fields in successful emulated responses were malformed because
`cgi-io` forks the guest `busybox md5sum` and `sha256sum` applets, and child
MIPS execution is not automatically QEMU-wrapped. File creation and ACL
decisions were unaffected.

## Genuine dnsmasq parser validation

The firmware's genuine `dnsmasq` 2.93 was run as root in a private namespace,
bound only to `127.0.0.1:25353`, with no upstream resolver.

`scripts/probe_openwrt_dnsmasq_security.py` exercised:

- empty and truncated packets;
- truncated questions;
- self-referential and two-node DNS compression loops;
- a label length greater than 63;
- a question count of 65,535;
- truncated and oversized EDNS option data;
- zero, excessive, truncated and undersized TCP frame lengths.

The daemon remained alive after all nine UDP and four TCP cases. A valid
control query returned a response after every malformed probe. No crash,
listener loss or persistent resource exhaustion was observed.

## Genuine wpad wired-EAPOL parser validation

The shipped `wpad` identifies itself as `wpa_supplicant v2.12-devel` and
includes both `nl80211` and wired Ethernet drivers. The genuine MIPS binary
was launched with its wired driver on one end of a disposable veth pair in a
private user and network namespace.

`scripts/probe_openwrt_wpad_eapol.py` sent 15 bounded EAPOL cases:

- empty, one-byte and truncated EAPOL headers;
- valid Start and Logoff controls;
- unknown EAPOL version and packet type;
- empty bodies with declared lengths of one and 65,535;
- short EAP, EAP length underflow and EAP length overflow;
- short and inconsistently sized EAPOL-Key inputs;
- a maximum-sized Ethernet payload.

It then sent a bounded burst of 64 truncated EAPOL-Key frames. An independent
raw socket on the target veth observed all 15 individual corpus frames.
The genuine `wpad` process remained alive after every case and after the
burst.

This validates the compiled wired receive path, not the `nl80211` 802.11
management-frame path. The image's ucode integration also logged that its
`ubus` module was unavailable in the direct QEMU host-path execution context;
the core supplicant initialized successfully despite that lab-only error.
No crash or persistent hang was observed.

## Genuine odhcpd DHCPv6 parser validation

A MIPS binfmt handler was registered only inside a disposable user, mount,
PID and network namespace. This enabled nested firmware executables without
altering host-global binfmt state. The genuine `odhcpd` was run in its
supported standalone (`-u`) mode, bound to UDP/547 on one end of a private
veth pair. The UCI DHCP section had to be named after the synthetic interface
for standalone activation.

The baseline gate succeeded: a valid DHCPv6 Solicit received an Advertise.
`scripts/probe_openwrt_odhcpd_security.py` then exercised:

- empty, short and unknown-message inputs;
- truncated option headers and 65,535-byte declared option lengths;
- short and duplicate client identifiers;
- short IA_NA and overflowing nested IA_NA options;
- short, empty and overflowing relay-forward options;
- relay hop count 255;
- correctly length-encoded relay nesting at depths 1, 4, 8, 16 and 32;
- minimal Request, Confirm, Renew, Rebind, Release and Decline messages;
- 256 zero-length options and a 1,400-byte inconsistent option body;
- a bounded burst of 128 malformed option-length packets.

The daemon log confirmed receipt of the corpus on the intended interface.
After every individual input and after the burst, a fresh valid Solicit
received an Advertise. The genuine daemon remained alive and UDP/547 stayed
bound. No crash, persistent hang or listener loss was observed.

## nl80211 management-frame harness status

The host kernel contains `mac80211_hwsim`, but the execution environment
cannot load kernel modules and passwordless privilege elevation is
unavailable. There is no existing physical or simulated nl80211 radio.
Consequently, no 802.11 management-frame coverage is claimed. The prior
wired-EAPOL result remains valid, but reaching the remaining nl80211 parser
requires physical hardware or a host where the software-radio module can be
loaded.

## Genuine LuCI ucode CGI validation

The earlier LuCI CGI execution gap was closed in a network-disabled
disposable container. The genuine MIPS `ubusd`, `rpcd`, `uhttpd`, `ucode`
interpreter, ucode extension modules and `/www/cgi-bin/luci` handler all ran
from the firmware filesystem. A small statically linked host-architecture
shebang adapter performed only the otherwise-missing MIPS child transition;
it preserved the CGI environment, standard streams, firmware interpreter,
modules and handler code.

The live rpcd stack exposed the expected `file`, `iwinfo`, `luci`,
`luci-rpc`, `network.rrdns`, `rc`, `rpc-sys`, `session`, and `uci` ubus
objects. An unauthenticated `luci.getFeatures` control call succeeded.

`scripts/probe_openwrt_luci_cgi_security.pl` sent 16 bounded pre-auth cases
through the genuine HTTP-to-CGI path:

- empty form input, malformed percent escapes and an encoded NUL;
- duplicate login fields, an 8 KiB form name and a 64 KiB form value;
- truncated and 256-level nested JSON;
- missing, truncated and 8 KiB multipart boundaries;
- literal and encoded dot segments, an encoded slash and an 8 KiB path.

The long boundary and long path were rejected with 413, the traversal cases
with 404, and the truncated multipart case with 502. The remaining cases
reached the same 500 response as the clean unauthenticated control. That
baseline 500 is a partial-lab artifact: LuCI reached its login-required
dispatcher, then attempted to render state normally supplied by the absent
`procd`/board runtime. It occurred before malformed probes and therefore was
not classified as a request-triggered crash.

After every case, a clean unauthenticated control request received an HTTP
response. The genuine `uhttpd`, `rpcd`, and `ubusd` processes remained alive.
No crash, listener loss, persistent resource exhaustion, authentication
bypass, file disclosure or command execution was observed.

## Full-system stock-init validation

A full-system MIPS VM was subsequently booted with
`qemu-system-mipsel -M malta`. QEMU does not implement the MediaTek MT7621
board, so the EW1200's shipped MT7621 kernel cannot boot faithfully on any
available QEMU machine. The full-system validation therefore used a Debian
6.1.0-50-4kc-malta kernel for emulated hardware support and the complete
EW1200 25.12.5 filesystem as the initramfs. This is genuine full-system CPU
and kernel execution of the firmware userspace, but it is not proof of
MT7621-specific kernel, flash, switch, PCI or radio behavior.

The filesystem was extracted directly from the SquashFS at offset 3,321,168
with `unsquashfs`. This mattered because the earlier recursive extraction
had defensively redirected absolute symlinks such as `/sbin/insmod` and
`/usr/bin/env` to `/dev/null`. The full-system image preserved the shipping
symlinks.

A minimal `/init` mounted the kernel filesystems, loaded the matching Malta
PCnet driver, configured the synthetic Ethernet interface, and handed PID 1
to the firmware's unmodified `/sbin/init`. The serial trace established:

- genuine OpenWrt `procd` running as PID 1;
- completion of preinit, root mounting, first-boot board-file generation,
  ubus initialization and normal init-script execution;
- genuine firmware `ubusd`, `logd`, `rpcd`, `netifd`, `hostapd`,
  `wpa_supplicant`, Dropbear and `uhttpd` processes;
- live `system`, `service`, `network`, `session`, `luci`, `file`, `uci` and
  related ubus objects;
- a complete LuCI login page through localhost-only forwarding, replacing
  the partial lab's missing-board-state 500 response.

QEMU networking used `restrict=on` and forwarded only
`127.0.0.1:28084` to guest TCP/80.

The eight-case uHTTPd parser corpus returned 400, 501, 403 or 413 as
appropriate. A clean static control request succeeded after every case.
The 16-case LuCI CGI corpus returned the normal unauthenticated 403 response
for control and form/JSON cases, 500 for a multipart request lacking a
boundary, 502 for a truncated multipart body, 413 for oversized boundary and
path cases, and 404 for traversal cases. A clean LuCI control response
succeeded after every case.

The boundary-less multipart 500 is a handled per-request error: the daemon
and complete stock-init guest remained available, and subsequent independent
requests succeeded. No process exit, listener loss, persistent hang,
authentication bypass, file disclosure or command execution was observed.
It is not an unauthenticated DoS.

## Version and public-prior-art context

OpenWrt 25.12.5 is the current stable release on the review date. Its
changelog records security and robustness fixes in the same surfaces under
review, including `cgi-io`, `uhttpd`, `rpcd`, `dnsmasq`, and `odhcpd`.
Consequently, older proof-of-concept behavior must not be transferred to this
image without direct reproduction.

No candidate in this pass reached the threshold for a novelty/zero-day claim.

2. expand multipart fuzzing with a coverage-guided native build of the same

3. expand odhcpd coverage with a coverage-guided native build matching this

4. exercise `wpad`'s `nl80211` management-frame path with mac80211_hwsim or

6. reproduce any crash on the genuine current image and check current public
