# GL.iNet GL-X3000 Spitz AX 4.8.3 security assessment

Date: 2026-07-24

Status: private security research; vendor coordination recommended

## Executive summary

Firmware 4.8.3 contains two independent authentication failures in its
root-privileged eSIM subsystem:

1. The router's LAN WebUI reverse-proxies `/sdk/v1` to the eSIM daemon without
   applying the normal administrator-session check. Read-only requests were
   dynamically confirmed without credentials, and the same handler exposes
   profile-changing operations.
2. The daemon maintains an outbound, plaintext TCP push connection and accepts
   an XXTEA-encrypted `sh_exec` message without authenticating the server or
   authorizing the command. The unmodified AArch64 daemon executed a marker
   command through `/usr/bin/sh -c` in an isolated emulator.

The second finding is a confirmed root command-execution vulnerability with
conditional WAN exploitability. An attacker who can intercept, redirect, or
control the outbound push connection can execute commands without possessing
router administrator credentials. Arbitrary off-path publication through
GL.iNet's production service has not been tested and must not be claimed.

## Classification at a glance

| Finding | Authentication | Impact | Reachability |
| --- | --- | --- | --- |
| `/sdk/v1` omission | None | eSIM disclosure and administrative operations; potential DoS | LAN HTTP/HTTPS by default |
| Push `sh_exec` | No server or per-command authentication | Root OS command execution | Outbound WAN channel; requires interception, redirection, server control, or an unproven service ACL bypass |
| Shared session lockout | None | Administrative WebUI DoS | LAN by default |

The push issue is not merely a denial of service: the marker file and
`execve("/usr/bin/sh", ...)` trace establish arbitrary shell-command execution.
DoS is a possible consequence of that root RCE.

## Scope and disposition

- Product: GL.iNet GL-X3000 Spitz AX
- Firmware: 4.8.3
- Firmware SHA-256:
  `877500360e81c65c8cb422ab7bcd9f3af14087f454da60434e93568c2e6f0e89`
- Root eSIM service: `/usr/bin/lpa_arm64_v1.50`
- Service SHA-256:
  `0c3436f9de9c32df46bb3f9c7f383a323ca0519abe58e72085873792b0f59c29`

Cross-image comparison additionally found:

- GL-XE3000 Puli AX 4.8.3 contains the exact same service SHA-256 and is
  therefore affected by the same device-side logic.
- GL-E750 firmware `4.0-release10326` contains an older MIPS `lpa_v1.41`
  implementation with the same endpoint, XXTEA library, and `sh_exec` /
  `sh_resp` strings. This is a static affected-code candidate, not a
  dynamically confirmed model.

All three inspected service binaries contain the same embedded login-signing
secret. This establishes globally reused client-side key material across the
X3000, XE3000, and older E750 implementations. It does not establish that the
production server accepts an arbitrary EID/IMEI, because that decision is
external to the firmware.

Root command execution through the firmware's push receive path is confirmed
in an isolated lab. Production push-service impersonation or ACL bypass is not
confirmed and requires vendor-authorized, two-device testing.

Two security findings were established:

1. a confirmed unauthenticated LAN administrative API that runs in a root
   eSIM daemon and exposes eSIM state, logs, and profile-changing methods; and
2. a confirmed command-execution trust-boundary flaw in the same daemon:
   XXTEA-encrypted JSON messages of kind `sh_exec` are passed to `sh -c`
   without per-message command authorization.

Arbitrary access to the upstream production push channel has not been shown.
The firmware vulnerability is confirmed; Internet exploitability remains
conditional on production authentication and device-isolation controls.

## Finding 1: unauthenticated root eSIM API

### Exposure and impact

This path is LAN-accessible through the router's ordinary HTTP/HTTPS service.
It is not directly WAN-accessible under the default configuration. Remote
administration, port forwarding, or another upstream proxy could expand that
exposure, but those configurations were not evaluated.

`/etc/nginx/gl-conf.d/esim.conf` defines:

```nginx
location /sdk/v1 {
    proxy_pass http://127.0.0.1:3456/sdk/v1;
}
```

Unlike `/rpc`, `/ws`, `/upload`, `/download`, and `/cgi-bin/`, this location
does not invoke `/usr/share/gl-ngx/oui-access.lua`.  Nginx's longest-prefix
selection means the generic authenticated `location /` does not protect it.

The backend is started as a normal procd service without a non-root user:

```sh
procd_set_param command /usr/bin/lpa_arm64_v1.50
```

The init script adds a firewall DROP for direct LAN access to TCP 3456, but
that rule does not protect the port-80/443 Nginx reverse proxy.  The backend
also contains no HTTP authentication.

The native AArch64 daemon was executed in a disposable QEMU/Docker lab and
bound only to host loopback.  These unauthenticated requests succeeded:

```http
POST /sdk/v1 HTTP/1.1
Content-Type: application/json

{"method":"running"}
```

```json
{"tx_id":"","code":200,"message":"ok","data":{"hint":"","running":false}}
```

`{"method":"progress"}` returned the installation progress object, and
`{"method":"log"}` returned the service's full operational log.  Decompilation
of `main.CtrlSdkV1` recovered additional accepted methods including
`install`, `enable`, `disable`, `delete`, `nick`, and `notify`. Those
mutating methods were exercised only against the disposable emulator, never
against hardware or a real eSIM service.

An additional end-to-end LAN test used the extracted firmware's AArch64 Nginx
binary, the exact vulnerable `/sdk/v1` location, and the extracted daemon in
one isolated router container. A separate container on the internal-only
Docker LAN sent the request with no Cookie, Authorization, or session header.
The proxy returned:

```http
HTTP/1.1 200 OK
Server: nginx/1.26.1
Content-Type: application/json

{"tx_id":"","code":200,"message":"ok","data":{"hint":"","running":false}}
```

This confirms the authentication omission through the LAN-facing reverse
proxy, rather than only through direct access to the backend.

The guarded read-only verifier is:

`scripts/x3000_esim_unauth_probe.py`

This is a confirmed broken authentication boundary with confidentiality and
eSIM-management integrity impact.  It is not, by itself, RCE.

### Direct LAN command-execution audit

A separate container on the internal-only LAN submitted a marker-only matrix
through the extracted Nginx and daemon. None of the requests contained a
Cookie, Authorization header, or session token.

| Method / field | Result | Marker |
| --- | --- | --- |
| `install.ac_code` | HTTP wrapper 200; daemon code 500 at connectivity preflight | absent |
| `install.cf_code` | HTTP wrapper 200; daemon code 500 at connectivity preflight | absent |
| `nick.name` | daemon code 200 | absent |
| `nick.iccid` | daemon code 400, invalid ICCID | absent |
| `enable.iccid` | daemon code 400, invalid ICCID | absent |
| `disable.iccid` | daemon code 400, invalid ICCID | absent |
| `delete.iccid` | daemon code 400, invalid ICCID | absent |
| `notify.iccid` | daemon code 200 | absent |

The ICCID handlers reject shell metacharacters before entering their native
profile operations. `nick.name` crosses the typed native
`IpaSetNickname` binding. The install parameters cross
`IpaDownloadInstall`; the decompiled profile wrappers call the native IPA
bindings and do not call `main.SysSh`.

The install handler does contain a separate shell invocation:

```text
ping -c %d %s | grep received
```

Its `%s` value is not supplied by the HTTP request. It is read from the
daemon's configuration and defaults to the fixed firmware constant
`34.196.94.121`. Static searches and emulator API testing found no
unauthenticated HTTP method that changes this field. Thus this is a shell sink
with a configuration-controlled argument, not a demonstrated LAN
request-to-shell path.

The QEMU user-mode harness reached this guard, but its child-process output
was not parsed successfully even after the IP was locally shadowed and
ordinary Internet connectivity was removed. Consequently, the activation-code
and confirmation-code values were not dynamically driven past the install
preflight. Their post-guard native path was reviewed statically. No marker,
unexpected child `execve`, daemon crash, or service loss was observed in the
completed matrix.

Current conclusion: the unauthenticated LAN administrative API is confirmed,
but no unconditional LAN RCE has been established. The two proven facts must
not be combined into a claim that `/sdk/v1` itself provides shell execution.

An exhaustive Ghidra cross-reference pass subsequently resolved every direct
caller of `main.SysSh`:

| Caller | Command provenance |
| --- | --- |
| `main.cleanLog` | internally constructed log paths and `rm` commands |
| install ping helper | fixed/configuration-derived ping count and address |
| `main.SysIsRmnetInUsing` | fixed `route | grep default | head -1` command |
| `main.(*PushService).handleShExec` | push-message command field |

`main.CtrlSdkV1` is not a direct `SysSh` caller. Its profile-changing branches
call the typed C/IPA wrappers described above.

The configuration path was also closed statically. `main.UpdateConfig` has one
external caller, `main.MsyncHandleResp`, in the remote synchronization
response path. `main.SaveConfig` is called by `UpdateConfig`; neither function
is called by `CtrlSdkV1`. Therefore the unauthenticated LAN API cannot, in this
firmware build, rewrite the ping or push fields and then pivot into one of the
configuration-derived command paths.

## Finding 2: push-to-shell RCE confirmed in an isolated lab

### Security boundary

This is not an inbound WAN listener. The router initiates the connection to
the push service, so an inbound firewall does not remove the exposure. The
device authenticates itself in its login request, but it does not
cryptographically authenticate the server response and does not validate an
independent signature or authorization token on `sh_exec`.

Accordingly:

- server interception or redirection is sufficient for root RCE;
- router-administrator credentials are not required after that precondition;
- production publisher access and cross-device ACL bypass remain unconfirmed;
- the defensible label is **confirmed root RCE with conditional WAN
  reachability**, not arbitrary unauthenticated Internet RCE.

Go 1.21 pclntab recovery identified the following exact functions:

```text
main.(*PushService).runRead    0x65e910
main.PushConnectState          0x65f400
main.(*PushService).loginReq   0x65fbe0
main.PushSyncState             0x6602b0
main.(*PushService).handleShExec 0x660ae0
main.SysSh                     0x663160
```

`PushSyncState` reads messages from the long-lived push connection, decrypts
an XXTEA-protected JSON payload, compares its `kind` to the seven-byte literal
`sh_exec`, and calls `handleShExec`.  That handler passes the message's
command field to `SysSh`; `SysSh` invokes Go's `os/exec` path with `sh -c`.
The command output is published back through the push service.

The daemon connects over raw TCP to `34.196.94.121:1887`.  The binary contains
a constant used to generate an MD5 login signature from IMEI, nonce, and
timestamp.  No TLS stack protects this connection and no second signature is
verified on an incoming `sh_exec` message in the recovered receive path.

The complete sink was confirmed against the unmodified extracted daemon in an
internal-only Docker network.  The lab assigned `34.196.94.121` to a local
replacement server, so the real vendor address was unreachable.  A pseudo-eUICC
advanced the daemon through its normal card-ready and long-sync states.

The recovered wire protocol is:

```text
control frame: 1-byte type
data frame:    type 5 || uint32be encrypted_length || XXTEA(JSON)
```

After the daemon's type-1 login, the lab server sent a one-byte type-2
acceptance, waited for the daemon's encrypted `sync_req`, and sent:

```json
{"kind":"sh_exec","tx_id":"friday-marker","data":"printf X3000_RCE_CONFIRMED >/tmp/x3000-rce-marker"}
```

The daemon logged the received object, created `/tmp/x3000-rce-marker`, and
the file contained exactly:

```text
X3000_RCE_CONFIRMED
```

Its returned `sh_resp` included the execution trace:

```text
execve("/usr/bin/sh",{"sh","-c","printf X3000_RCE_CONFIRMED >/tmp/x3000-rce-marker",NULL})
```

This confirms command execution through the push channel without an
incoming-message signature or command authorization check.  It does not by
itself prove that an arbitrary Internet client can reach or impersonate the
production push service; production service ACLs were not tested.

Reproduction components:

- `scripts/x3000_push_lab_server.py`
- `scripts/x3000_lpa_tty_harness.py`

The real vendor endpoint was not contacted or tested.

The replacement server did not possess or send a server credential. Its entire
login acceptance was the one-byte type-2 control response. The daemon then
entered synchronization and accepted `sh_exec`. This directly confirms absent
server authentication on the device side; it is not an inference from the
production service.

### Attack scenarios

Confirmed by device-side behavior:

1. An attacker gains a position capable of redirecting or intercepting the
   router's plaintext push TCP connection.
2. The attacker accepts the daemon's login with the single-byte type-2 control
   response; the router performs no server certificate or challenge check.
3. After receiving `sync_req`, the attacker supplies an encrypted `sh_exec`.
4. The daemon executes its `data` field through `sh -c` as root.

Not confirmed:

- an arbitrary off-path client authenticating to the production service;
- Device A publishing to Device B;
- production acceptance of replayed or fabricated device logins;
- direct inbound WAN reachability to the local eSIM HTTP API.

The vendor-authorized procedure for resolving these questions is documented
in `private_disclosures/GL-X3000/X3000_PRODUCTION_ACL_VALIDATION_PLAN.md`.

### Attempts to remove the reachability precondition

The following non-production checks were completed:

- Default firewall policy rejects WAN-zone input. No default WAN accept rule
  for TCP 80, 443, or 3456 was found.
- Nginx listens on all addresses, but default WAN firewall rejection prevents
  treating `/sdk/v1` as directly Internet-accessible.
- The eSIM init script adds an explicit TCP 3456 drop for the LAN zone. The
  unauthenticated `/sdk/v1` path remains reachable through LAN WebUI ports.
- Static searches found no unauthenticated handler that writes the push
  hostname, IP, route, or DNS configuration.
- Disposable, network-disabled API requests using `method:"config"` did not
  write `/root/esim/conf.json` or alter the push destination; they entered an
  eSIM operation and timed out waiting for modem state.
- X3000, byte-identical XE3000, and older E750 service binaries reuse the same
  embedded client login secret.

These results strengthen the authentication design finding but do not remove
the off-path reachability condition. No unconditional arbitrary-Internet
chain was established.

### Suggested severity

The device-side result has complete confidentiality, integrity, and
availability impact once the push-channel precondition is satisfied. A
provisional CVSS v3.1 representation is
`AV:N/AC:H/PR:N/UI:N/S:U/C:H/I:H/A:H` (8.1 High), where high attack complexity
reflects the currently required interception/redirection or server control.
If an authorized test proves arbitrary production publication or
authentication bypass, attack complexity may need reevaluation.

## Shared GL.iNet finding

The 4.8.3 `/usr/sbin/gl-ngx-session` is byte-identical to the GL-MT5000 4.8.6
build.  The previously confirmed process-global ten-failure WebUI lockout
therefore applies to this firmware too.  That is an unauthenticated
administrative-plane DoS, not RCE.

## Public-prior-art check

A dated web search on 2026-07-24 located public GL.iNet forum material
identifying TCP 3456 as the eSIM service and showing the daemon's connection
to `34.196.94.121:1887`.  It did not locate a public report of:

- the Nginx `/sdk/v1` authentication omission;
- unauthenticated eSIM profile control through ports 80/443; or
- the `sh_exec` push-to-shell control flow.

This is only a preliminary novelty check.  CVE, vendor-ticket, and coordinated
duplicate review remain necessary before using the term zero-day.

The search did locate unrelated GL-X3000 issues, including CVE-2024-20017 and
CVE-2025-2851, plus GL.iNet's April 2025 security advisory. Their published
descriptions concern different components and do not describe the eSIM
`sh_exec` channel. Public-search non-discovery cannot exclude a private report
or undisclosed vendor duplicate.

## Remediation

- Add the normal WebUI access hook to the exact `/sdk/v1` location and require
  a valid administrator session at the backend as defense in depth.
- Bind the backend to loopback only and remove unnecessary direct exposure.
- Remove remote shell execution from the eSIM push protocol.
- If remote diagnostics are essential, use mutually authenticated TLS,
  per-device credentials, strict server-side tenant/topic ACLs, signed
  allow-listed diagnostic operations, audit logs, and explicit local consent.
- Rotate the embedded push-signing secret and treat every shipped copy as
  recoverable by an attacker.

## Limitations

- Only the identified GL-X3000 4.8.3 image was dynamically confirmed. The
  byte-identical GL-XE3000 binary establishes code equivalence but was not
  separately emulated.
- No physical eSIM profile mutation was performed.
- No traffic was sent to the real vendor push endpoint.
- Production authentication, tenant separation, and publisher ACLs were not
  evaluated.
- The preliminary public-prior-art search is not a formal duplicate or CVE
  determination.

## Disclosure recommendation

Provide GL.iNet with the firmware and service hashes, isolated transcript,
marker proof, and reproduction scripts under coordinated disclosure. Ask the
vendor to reproduce the production ACL cases in staging, identify every model
shipping the same service, rotate shared material, and issue fixed firmware
before public technical details or protocol secrets are released.
